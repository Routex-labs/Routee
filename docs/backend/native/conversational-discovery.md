# 대화형 매장 탐색·추천 — 구현 전 설계

작성일: 2026-07-29

상태: Planning

기존 자연어 검색은 사용자의 문장과 가장 가까운 매장 **1건**을 목적지로 확정한다.
이 방식은 `"탠디 어디야?"`처럼 목적지가 명확할 때는 적합하지만, `"신발"`,
`"명품"`, `"밥집"`처럼 여러 후보가 자연스러운 질의에는 적합하지 않다.

이 문서는 단일 목적지 검색을 없애는 문서가 아니다. **명확한 질의는 바로 안내하고,
모호한 질의는 선택지를 물어본 뒤 여러 후보를 추천하는 탐색 흐름**을 추가하기 위한
구현 전 기준을 정한다.

관련 문서:

- 경량 문자열 검색: [query.md](query.md)
- 경량 + FAISS 의미 검색: [FAISS.md](FAISS.md)
- 현재 Flutter 연동: [client-handoff.md](client-handoff.md)

## 1. 현재 문제

### 1-1. API가 여러 후보를 표현하지 못한다

현재 `POST /query/ai`는 `DestinationResponse`를 사용하며 `match` 한 건만 반환한다.
백엔드도 경량·FAISS 후보 중 최상위 한 건을 즉시 확정한다.

따라서 `"명품"`에 관련 매장이 수십 개 있어도 한 매장만 보이고, `"신발"`에는
나이키·아디다스·탠디처럼 성격이 다른 후보가 있어도 유사도 최상위 한 곳만 보인다.
이는 검색기의 top-1 결과이지 사용자 취향을 반영한 추천이 아니다.

### 1-2. 의미 검색이 엔터 + 경량 빈손이라는 두 조건을 모두 통과해야만 돈다

현재 Flutter 상단 검색([`search_panel.dart`](../../../client/lib/screens/map_shell/widgets/search/search_panel.dart))은
타이핑 중 `POST /query/destination`만 호출한다. `POST /query/ai`는 `submitTick`이 올라간
확정 시점에, 그것도 `results.isEmpty && building == null`일 때만 이어 붙는다
(`_search(..., allowSemantic: true)`).

먼저 이미 되어 있는 것부터 구분한다. 의미 검색 진행 중에는 `_searchingSemantic`으로
`"뜻이 비슷한 매장을 찾는 중…"`을 따로 띄우고, 결과에는 `"뜻이 비슷한 매장을 찾았어요"`
배너를 얹는다. 늦게 도착한 응답도 `_requestId` 순번으로 버린다. 즉 "AI가 도는 중인지
모른다"·"과거 응답이 덮는다"는 이미 해결돼 있고, 남은 문제는 **언제 도는가**다.

- 타이핑 중 경량이 빈손이면 `_emptyState`가 곧바로
  `"…에 맞는 매장을 찾지 못했어요 / 다른 말로 바꿔서 다시 찾아보세요"`를 띄운다.
  `"신발"`은 어떤 매장명·카테고리와도 정확히 일치하지 않으므로(1-4 참고) 타이핑만으로는
  항상 이 화면이 나온다. AI를 아직 부르지도 않은 상태의 문구가 최종 결론처럼 읽힌다.
- 한글 IME에서 첫 엔터가 조합 확정에 쓰이면 `onSubmitted`가 실행되지 않아 `submitTick`이
  오르지 않는다. 그러면 의미 검색은 아예 시작되지 않는다.
- 경량이 한 건이라도 잡으면(`results.isNotEmpty`) 의미 검색은 건너뛴다. 지금은 그래도
  됐지만, 탐색 흐름에서는 **경량이 잡은 그 한 건이 오히려 틀린 확정**이다(1-4).

### 1-3. `/query/ai` 호출부가 화면 두 곳이다

계약을 바꿀 때 고쳐야 할 클라이언트 지점은 상단 검색 하나가 아니다.

| 호출부 | 진입 | `current_floor_id` | 비고 |
|---|---|---|---|
| [`search_panel.dart`](../../../client/lib/screens/map_shell/widgets/search/search_panel.dart) | 상단 검색창 엔터 | 보내지 않음(건물 전체) | 경량 빈손일 때만 |
| ~~`ai_search_sheet.dart`~~ **(삭제됨)** | 경로 안내 화면 FAB | 현재 층을 보냄 | 질의–응답 로그를 쌓는 시트 |

둘 다 [`http_destination_repository.dart`](../../../client/lib/repositories/place/http_destination_repository.dart)의
`searchDestinationsAi` 하나를 공유하고, 이 메서드는 `/query/destination`과 파싱까지
공유한다(`_query`). 따라서 `/query/ai` 응답 모양을 바꾸면 파서 한 곳이 아니라
**추상 인터페이스(`destination_repository.dart`)·mock·두 화면·관련 테스트**가 함께 움직인다.
> **`ai_search_sheet.dart`와 `directions_sheet.dart`는 그 뒤 삭제됐다**(실내 안내를 공용
> 세션으로 모으고 실내 탭을 없앤 리팩터, 그리고 길찾기 입력을 상단 바 두 칸으로 되돌린
> 변경). 이 문서에서 그 파일들을 가리키는 서술은 **당시 상태**이며, 지금 `/query/ai`를
> 쓰는 곳은 [`search_panel.dart`](../../../client/lib/screens/map_shell/widgets/search/search_panel.dart)(상단 검색)와
> [`map_shell_screen.dart`](../../../client/lib/screens/map_shell/map_shell_screen.dart)의
> 길찾기 후보 조회 두 곳이다. 아래 "두 화면"이라는 표현도 그 전제에서 읽어야 한다.

9절의 화면 상태는 상단 검색 패널 기준이며, `ai_search_sheet`를 같은 계약으로 옮길지
탐색 진입점을 상단 검색 한 곳으로 합칠지는 12절 미결로 둔다.

### 1-4. 경량 1차가 모호한 질의를 이미 한 건으로 확정해 버린다

이게 가장 먼저 걸리는 문제다. `match_ai_destination`은 2차 의미 검색에 넘기기 전에
`_is_confident_light_match(scored)`로 경량 결과를 확정하는데, 이 함수는
**tier 2(이름 부분 일치)만 모호성을 따진다.** tier 0(정확 이름)·tier 1(카테고리·소분류
정확 일치)은 후보가 몇 건이든 무조건 확정이다(`if best_tier < 2: return True`).

`_tier`는 질의가 `category`나 `subcategory`와 정확히 같으면 tier 1을 준다. 그런데 이
문서가 예시로 드는 모호한 질의 상당수가 바로 소분류 값 자체다.

| 질의 | 현재 판정 | 실제 후보 수(2026-07-29 시드) |
|---|---|---|
| `명품` | tier 1 → direct 확정 | 43 |
| `레스토랑` | tier 1 → direct 확정 | 65 |
| `슈즈` | tier 1 → direct 확정 | 8 |
| `신발` | 미일치 → 2차 의미 검색 | — |
| `밥집` | 미일치 → 2차 의미 검색 | — |

즉 `"명품"`이 한 매장만 보이는 원인은 응답 모델이 `match` 하나만 담아서가 아니라,
그 앞에서 **43건 중 `(level, store.id)` 정렬 첫 매장으로 확정**되기 때문이다.
7-2의 처리 순서를 문자 그대로 구현하면(2단계에서 direct 확정, 3단계에서 facet 해석)
`"명품"`은 여전히 clarify에 도달하지 못한다. 확정 조건을 tier 1까지 넓혀 고쳐야 한다
(7-2 참고).

### 1-5. 현재 분류는 추천용 다중 속성이 아니다

`Store`의 분류 필드는 `category`, `subcategory` 두 개뿐이다. 이 값은 지도와
카테고리 목록에 표시할 대표 분류이지, 매장이 제공하는 상품과 사용 상황을 모두
표현하는 태그가 아니다.

2026-07-29 로컬 시드 데이터의 확인 예시는 다음과 같다. 이 수치는 데이터가
편집되면 바뀌므로 구현 상수로 사용하지 않는다.

- `subcategory="슈즈"`: 8개
- 나이키 라이즈·아디다스 스타디움: `캐주얼·스트리트`
- 나이키 골프: `골프`
- 나이키스윔: `스포츠·아웃도어`
- `category="식음료"`의 소분류: 레스토랑(65), 카페·베이커리(41), 식품·그로서리(19), 와인·주류(9)
- 한식·일식·중식·양식, 메뉴, 가격대, 혼밥·가족식사 같은 추천 속성은 없음

`"신발"`을 `subcategory="슈즈"`로만 필터링하면 나이키·아디다스가 빠진다.
`"밥집"`을 `subcategory="레스토랑"`으로만 좁히면 음식 종류를 물을 근거가 없다.

### 1-6. 태깅 대상 규모 — 전 매장이 아니다

같은 시드 데이터를 `store_categories.json`·`store_category_by_name.json` 오버라이드까지
적용해 세면 다음과 같다. 이 숫자는 5절의 수작업 태깅 비용과 11절 Phase 1 범위를
정하는 근거이므로 함께 남긴다.

> **이 표는 이때의 기록이다.** 2026-08-17 전수 재조사로 `식음료`가 셋으로 갈리고
> `서비스` 대분류가 없어졌다 — 태깅 상한 539건이라는 결론은 그대로다(편의시설을
> 뺀 수가 515건으로 조금 줄었다). 지금 분포는
> [매장 카테고리 전수 재조사](../store-category-resurvey.md).

| 대분류 | 건수 | 태깅 필요 |
|---|---|---|
| 편의시설 | 1101 (주차 787 · escalator 152 · elevator 68 · facility 52 · restroom 27 · 교통 7) | 아니오 |
| 패션 | 266 | 예 |
| 식음료 | 134 | 예 |
| 리빙 | 52 | 예 |
| 뷰티 | 36 | 예 |
| 서비스 | 30 | 조건부 |
| 키즈 | 21 | 예 |
| 합계 | 1640 | 편의시설 제외 **539** |

두 가지가 따라온다.

- **수작업 태깅은 539건이 상한이고, Phase 1의 신발·식음료 시범 범위는 200건 미만이다.**
  전 매장 1640건을 태깅하는 작업으로 잡으면 안 된다.
- **임베딩 코퍼스의 3분의 2가 편의시설이다.** 화장실·엘리베이터·에스컬레이터는 같은
  이름이 층마다 별도 Store 행으로 존재한다(엘리베이터·에스컬레이터 12개 층, 화장실 11개 층).
  7-2의 다양성 보정은 "브랜드 쏠림"만이 아니라 **이 동일 이름 시설이 추천 목록을 채우는
  것**을 먼저 막아야 한다.

## 2. 실패 조건을 먼저 정의

| 실패 조건 | 사용자 피해 | 방지 기준 |
|---|---|---|
| 모호한 질의를 한 매장으로 즉시 확정 | 선택권이 사라지고 추천을 신뢰하기 어려움 | 후보가 넓으면 `clarify`로 질문 |
| 매장명만 보고 음식 종류·가격대를 추측 | 실제와 다른 정보 안내 | 검증된 태그만 필터·문구에 사용 |
| `신발=슈즈`처럼 단일 소분류만 검색 | 나이키·아디다스 등 유효 후보 누락 | 상품 의도를 다중 `intents`로 별도 관리 |
| 질문을 연속해서 너무 많이 함 | 사용자가 검색을 포기 | 질문은 한 번에 한 축, 항상 `전체 보기` 제공 |
| 결과가 없는데 계속 세분화 질문 | 막다른 흐름 | 남은 후보 수가 0이면 이전 선택 해제·전체 결과 안내 |
| 정확한 브랜드명에도 취향을 다시 물음 | 빠른 목적지 검색이 느려짐 | 정확 이름은 기존 direct 흐름 유지 |
| 타이핑 중 `"결과 없음"`을 최종 결과처럼 표시 | AI 미호출을 실패로 오해 | 의미 검색 전에는 최종 없음 문구 금지 |
| 첫 의미 검색 인덱스 빌드가 길게 걸림 | 앱이 멈춘 것으로 인식 | 준비 상태를 분리 표시하고 인덱스 워밍 측정 |
| 추천 이유가 실제 태그와 다름 | 설명 신뢰도 하락 | `reason`은 일치한 검증 태그에서만 조립 |
| 태그 JSON과 매장 데이터가 드리프트 | 삭제 매장 추천·신규 매장 누락 | 시드 검증에서 고아 ID·미분류·허용값 검사 |
| 전체 태그 원본을 클라이언트에 전달 | 계약 비대화·출처 분산 | 질의에 필요한 option·match만 API로 반환 |
| 선택 취향을 서버에 불필요하게 장기 저장 | 개인정보·상태 관리 복잡도 증가 | 1차는 Flutter 검색 세션 안에서만 유지 |
| 소분류와 글자가 같은 질의를 경량이 direct로 확정 | `"명품"`·`"레스토랑"`이 43·65건 중 첫 매장으로 고정 | `_is_confident_light_match`를 tier 1까지 확장(1-4) |
| 동일 이름 시설이 추천 목록을 채움 | 화장실·엘리베이터가 층별로 12건까지 반복 노출 | 다양성 보정에 이름 기준 중복 제거 포함 |
| 모델 미가용과 임계값 미달을 같은 결과로 처리 | `degraded`와 `no_match`를 구분해 안내할 수 없음 | `semantic_search`가 실패 사유를 구분해 반환 |
| 인덱스 빌드 후 시드가 갱신됨 | option `count`는 새 데이터, 관련도는 옛 인덱스 | 시드·facet 변경 시 `reset_indexes()` 경로 확보 |

## 3. 목표와 비목표

### 목표

1. 정확한 매장명은 기존처럼 바로 한 건을 안내한다.
2. 범위가 넓은 질의는 사용자가 선택할 수 있는 질문과 후보를 함께 보여준다.
3. 후속 선택으로 후보를 좁히고, 최종 매장을 고르면 기존 경로 안내로 연결한다.
4. 추천 문구와 이유는 사람이 검증한 태그에 근거한다.
5. 기존 `POST /query/destination`과 온디바이스 Dijkstra 계약은 유지한다.

### 비목표

- 자유 대화를 생성하는 LLM 챗봇
- 매장에 없는 상품·메뉴·가격의 추측
- 사용자 프로필의 계정 단위 영구 저장
- 광고·프로모션·실시간 재고·혼잡도 추천
- 서버 최단 경로 계산

초기 버전은 생성형 문장 대신 정해진 문장 템플릿과 선택 chip을 사용한다.
검색·추천 근거가 안정된 뒤 문장 표현만 생성형 모델로 다듬는 것은 후속으로 검토한다.

## 4. 목표 사용자 흐름

### 4-1. 목적지가 명확한 질의

```text
사용자: "탠디 어디야?"
시스템: 탠디 · 3F
        [매장 보기] [길찾기]
```

- 정확 이름·강한 단일 일치이면 `direct`.
- 추가 질문을 하지 않는다.
- 기존 `entrance_node_id` 기반 길찾기 흐름을 그대로 사용한다.

### 4-2. 상품 범위가 넓은 질의

```text
사용자: "신발"
시스템: 어떤 신발을 찾으세요?
        [스포츠] [캐주얼] [명품] [전체 보기]

        이런 매장도 있어요
        - 탠디 · 3F
        - 지미추 · 2F
        - 크록스 · (층)
```

- 질문을 보여주면서도 서로 다른 성격의 초기 후보를 함께 제공한다.
- 한 브랜드·한 층·같은 이름에 결과가 몰리지 않도록 다양성을 보정한다.
- 사용자가 `전체 보기`를 선택하면 추가 질문 없이 목록을 보여준다.

> **이 화면은 아직 데이터로 재현할 수 없다.** 초판은 후보로 나이키 라이즈·아디다스
> 스타디움을 적었는데, 둘 다 소분류가 `캐주얼·스트리트`이고 **신발을 판다는 근거가
> 데이터 어디에도 없다.** 근거 있는 신발 후보는 `subcategory="슈즈"` 8건(지미추·골든구스·
> 캠퍼투게더 스토어·탠디·락피쉬 웨더웨어·버켄스탁·어그·크록스)뿐이다.
> 위 chip의 스타일 값도 슈즈 8건에는 소분류로 유도되지 않아 개별 검수가 필요하다.
> `구두·정장`은 chip에서 뺐다 — 신발(구두)과 의류(정장)를 한 값에 섞었고 `구두`는
> 이름 근거 후보가 0건이다. 검수 항목은 11절 Phase 1의 워크시트로 관리한다.

### 4-3. 음식 범위가 넓은 질의

```text
사용자: "밥집"
시스템: 어떤 종류가 좋으세요?
        [한식] [일식] [중식] [양식] [간단히] [상관없어요]

사용자: "일식"
시스템: 일식으로 찾았어요.
        - (검수로 일식이 확인된 매장)
        - ...
```

- 화면에 보이는 선택지는 현재 건물에 실제 후보가 있는 값만 만든다.
- 음식 종류가 없는 건물에서 빈 `중식` chip을 만들어서는 안 된다.

> **초판의 `긴자 바이린 → 일식·돈카츠`는 검증되지 않은 추측이었다.** 이름에 들어 있는
> 건 지명 `긴자`뿐이고, 돈카츠라는 근거는 데이터에 없다. 2절이 금지한 "매장명만 보고
> 음식 종류를 추측"에 그대로 해당한다.
>
> 레스토랑 65건 중 **이름만으로 cuisine을 확정할 수 있는 건 14건(21.5%)뿐**이고
> **49건(75%)은 사람 검수가 필요하다.** 따라서 이 흐름은 검수가 끝나기 전에는 동작하지
> 않으며, **설계 문서의 예시를 테스트의 기대 결과로 사용해서는 안 된다.**
>
> `식사` intent의 후보 집합은 `category="식음료"`(134건)가 아니라
> `subcategory="레스토랑"`(65건) 기준이어야 한다. 전자로 잡으면 `"밥집"` 질의에
> 야채·정육·수산 매장이 섞인다.

### 4-4. 후속 취향

초기 버전은 한 번에 한 축만 묻는다.

```text
"가까운 곳"    → 현재 층 또는 이동 비용을 정렬 보조로 사용
"간단히"       → occasion/menu 태그로 필터
"아무거나"     → 후보를 다양화해 바로 결과
"다시 선택"    → 직전 facet을 해제하고 질문으로 복귀
```

## 5. 데이터 원본 — 검색 전용 facet JSON

지도·카테고리 표시용 `category/subcategory`는 유지한다. 추천용 속성은 다음 파일을
새로운 수작업 원본으로 둔다.

```text
backend/resources/store_search_facets.json
```

Studio 원본 층 JSON을 직접 수정하지 않는 이유:

- Studio 데이터를 다시 추출하면 수작업 태그가 덮일 수 있다.
- 한 매장은 지도상 대표 소분류 하나와 검색 의도 여러 개를 동시에 가질 수 있다.
- 추천 데이터의 검수 책임과 변경 이력을 별도로 확인하기 쉽다.

### 5-0. 이미 같은 패턴이 돌고 있다

이 구조는 새 발명이 아니다. 저장소에는 이미 같은 모양의 수작업 오버라이드가 있고,
경로 규약(`backend/resources/`)도 여기서 온다.

| 파일 | 키 | 값 | 용도 |
|---|---|---|---|
| `resources/store_categories.json` | `store_id` | `{name, category, subcategory}` | 카테고리 오버라이드 1순위 |
| `resources/store_category_by_name.json` | 매장명 | `{category, subcategory}` | 폴백 |
| `resources/query_synonyms.json` | 별칭 | 표준어 | 경량 매칭 동의어 |

`store_categories.json`은 `store_id`를 키로, `name`을 사람이 diff를 보기 위한 중복
정보로 두는 방식까지 이 문서의 5-1과 동일하다. 즉 5-1의 스키마 결정은 이미 검증된
관례를 따르는 것이고, 로더도 `studio_adapter._load_store_categories`와 같은 자리에
붙는다. **다만 두 가지를 그대로 따라가면 안 된다.**

- 기존 로더는 파일이 없으면 `{}`로 조용히 넘어가고 **아무 검증도 하지 않는다.**
  5-2의 검증은 기존 파일 쪽에는 없는 새 요구다. 같은 디렉터리에 검증하는 파일과
  검증하지 않는 파일이 섞이는 셈이므로, 검증기를 facet 전용으로 만들지
  `store_categories.json`까지 함께 검사할지 먼저 정한다.
- 기존 파일은 매장명 폴백을 둔다. facet은 **폴백을 두지 않는다.** 매장명은 층마다
  중복되고(화장실 11개 층), 이름으로 태그를 붙이면 12개 층 시설에 같은 취향 태그가
  일괄로 붙는다.

`store_id`를 조인 키로 쓰는 근거도 데이터로 확인했다. 2026-07-29 시드 기준
12개 층 1640건의 `id`는 층을 가로질러 **중복이 없다**(`studio_adapter._reshape_stores`가
네임스페이싱 없이 원본 id를 그대로 쓰는 것과 일치). 남는 위험은 중복이 아니라
**Studio 재추출 시 `PO-…` id가 보존되는지**이며, 이는 `store_categories.json`이 이미
지고 있는 위험과 같다.

### 5-1. 제안 스키마

```json
{
  "version": 1,
  "vocabulary": {
    "intents": ["신발", "의류", "식사", "카페", "선물"],
    "styles": ["스포츠", "캐주얼", "구두·정장", "명품"],
    "cuisines": ["한식", "일식", "중식", "양식", "동남아", "분식"],
    "menus": ["밥", "면", "고기", "해산물", "샐러드", "디저트"],
    "occasions": ["혼밥", "가족식사", "데이트", "간단히", "포장"],
    "audiences": ["성인", "아동", "남성", "여성"]
  },
  "stores": {
    "PO-나이키매장ID": {
      "name": "나이키 라이즈",
      "intents": ["신발", "의류"],
      "styles": ["스포츠", "캐주얼"],
      "audiences": ["성인"]
    },
    "PO-긴자바이린ID": {
      "name": "긴자 바이린",
      "intents": ["식사"],
      "cuisines": ["일식"],
      "menus": ["고기"],
      "occasions": ["혼밥", "가족식사"]
    }
  }
}
```

규칙:

- 실제 키는 매장명보다 안정적인 `store_id`를 사용한다.
- `name`은 사람이 diff를 검토하기 위한 중복 정보이며 조인 키로 사용하지 않는다.
- 태그 값은 반드시 같은 파일의 `vocabulary`에 선언한다.
- 빈 배열은 저장하지 않는다.
- 가격대는 공식 메뉴·매장 자료처럼 확인 가능한 근거가 준비된 뒤 추가한다.
- 복수 매장이 한 Store 레코드에 합쳐진 원천 데이터는 먼저 데이터 분리 가능성을 검토한다.

### 5-1-1. 실제 구현 — 파생 + 오버레이 2층

5-1은 "모든 태그를 손으로 적는 한 파일"을 전제했는데, 데이터 조사 결과 그 전제가 틀렸다.
**`styles` 204건은 소분류에서 결정적으로 유도된다.** 손으로 옮겨 적으면 같은 정보가 두 벌이
되고 드리프트한다. 그래서 아래 2층 구조로 구현했다. `store_categories.json`의
"원본 + 오버라이드"와 같은 패턴이다.

```text
1층 파생 — app/repositories/store_facets.py  (코드 상수)
   스포츠·아웃도어 → ["스포츠"]      캐주얼·스트리트 → ["캐주얼"]
   컨템포러리     → ["컨템포러리"]   명품           → ["명품"]
   골프           → ["골프"]
   → 실데이터 1640건 중 204건이 여기서 결정된다(검증 완료)

2층 오버레이 — resources/store_search_facets/*.json  (수작업)
   파생으로 안 되는 것만. 축 단위로 파생을 이긴다.
   예: 슈즈 8건의 styles는 소분류가 알려주지 않으므로 개별 지정
```

`_`로 시작하는 파일은 어휘 선언이고(`_vocabulary.json`), 나머지 JSON은 카테고리별 오버레이다.
한 파일에 539건을 몰면 PR diff를 사람이 검수할 수 없어 분할했다. 같은 `store_id`가 두 파일에
나오면 오류다.

Phase 1의 vocabulary는 `styles` 하나뿐이다.

| 축 | Phase 1 | 이유 |
|---|---|---|
| `styles` | `["스포츠","캐주얼","컨템포러리","명품","골프"]` | 소분류에서 파생 |
| `cuisines` | 제외 | 레스토랑 65건 중 49건이 검수 대기 |
| `intents` | vocabulary 밖 별도 파일 | 매장별 배열이 아니라 소분류 규칙 + 예외로 확정(아래) |
| `menus` | 제외 | 식사쪽 이름 근거 6/65뿐 |
| `occasions` | 제외 | 이름 근거 0건 |
| `audiences` | 제외 | `성인`은 무의미, `남성`/`여성`은 부분 관측이라 필터로 쓰면 미표기 매장이 통째로 사라짐 |

5-1 예시에서 뺀 값: `구두·정장`(신발+의류 혼재, `구두` 후보 0건), `동남아`(후보 0건).
`아웃도어`는 `스포츠`에서 분리하지 않는다 — 소분류가 이미 `스포츠·아웃도어`로 합쳐 놓았고,
이름으로 가르면 31건 중 절반만 갈라져 나머지가 chip에서 사라진다.

`intents`는 이후 **소분류 규칙 객체 + 예외 매장 id**로 스키마를 확정했고(12절), 매장별
태그가 아니므로 vocabulary와 오버레이 어느 쪽에도 넣지 않고 `_intents.json` 한 파일에
둔다. 매장별 배열(`"intents": ["신발"]`)로 손으로 적으면 `styles`에서 이미 겪은 드리프트가
그대로 재현되기 때문이다(근거는 `app/repositories/store_facets.py` 모듈 docstring
"왜 intents는 매장 태그가 아니라 '규칙 + 예외' 파일인가"). 시드가 규칙 전개 결과를
`Store.search_facets["intents"]`에 적재하고 경량 매칭과 임베딩 문서가 그것을 소비한다.
**선언 목록과 건수는 `_intents.json`이 단일 출처다** — 여기 옮겨 적으면 태깅 라운드마다
낡는다. 확장 이력은 [facet-llm-tagging.md](facet-llm-tagging.md)를 본다.

### 5-2. 시드 검증

`reset_and_seed`에서 다음을 실패로 처리한다.

1. `version` 미지원
2. 존재하지 않는 `store_id`
3. JSON의 `name`과 실제 Store 이름 불일치
4. vocabulary에 없는 태그
5. 같은 배열 안의 중복 태그
6. 문자열이 아닌 태그 값

태그가 아직 없는 매장은 시드 전체를 실패시키지 않는다. 대신 커버리지 보고서에 남긴다.
신규 매장 추가 때 누락을 인지할 수 있도록 건물별·대분류별 태그 적용률을 출력한다.

## 6. 런타임 데이터 모델

수작업 JSON은 원본이고 DB는 실행용 사본이다. 초기 구현은 `Store`에 JSON 타입의
`search_facets` 필드를 추가하는 방안을 기본안으로 둔다.

```text
Store
├─ id
├─ name
├─ category / subcategory
├─ search_facets
│  ├─ intents[]
│  ├─ styles[]
│  ├─ cuisines[]
│  ├─ menus[]
│  ├─ occasions[]
│  └─ audiences[]
└─ entrance_node_id / coordinates
```

선택 근거:

- 현재 데모는 `reset_and_seed` 방식이라 별도 마이그레이션 호환 부담이 작다.
- 건물 단위 매장 수가 작고 기존 검색도 매장 목록을 메모리에서 평가한다.
- 태그 축이 추가될 때마다 nullable 컬럼을 늘리지 않아도 된다.
- 층 지도 응답은 명시적으로 필드를 조립하므로 검색 태그를 자동 노출하지 않을 수 있다.

근거를 코드로 확인한 부분은 다음과 같다.

- `Store.polygon`이 이미 `mapped_column(JSON)`이라 JSON 컬럼 추가는 새 패턴이 아니다.
- 층 지도 응답은 `building_queries._to_store_dict`가 필드를 하나씩 나열해 조립하고
  `dto/floor_map.py`도 필드를 명시하므로, 컬럼을 추가해도 자동 노출되지 않는다.
- 검색은 `query_search._load_stores`가 건물 전체를 메모리로 올려 평가하므로,
  facet 필터도 같은 자리에서 파이썬으로 처리된다. 건물당 1640건 규모에서는 충분하다.

태그 규모가 커지고 SQL에서 facet 집계·필터를 많이 수행하게 되면
`store_search_facets(store_id, facet_type, value)` 테이블로 정규화한다. 초기부터
별도 테이블을 도입하지는 않는다.

### 6-1. 인덱스 캐시 무효화

`query_semantic._indexes`는 `building_id`별로 **최초 질의 때 한 번 빌드해 프로세스가
살아 있는 동안 유지된다.** 비우는 경로는 `reset_indexes()` 하나이고 지금은 테스트만 쓴다.

facet을 인덱스 문서에 넣으면(7-1) 이 캐시가 태그의 사본을 들고 있게 된다. 서버를 띄운
채 `reset_and_seed`를 다시 돌리면 option `count`는 새 DB에서, 관련도 정렬은 옛 인덱스에서
나온다. 개발 중에 태그를 고치며 검증할 때 바로 부딪히는 문제이므로 Phase 2에서 함께 정한다.
최소한 재기동으로 해소된다는 사실을 검증 절차에 적고, 가능하면 시드 후 캐시를 비우는
경로를 만든다.

## 7. 검색과 추천 처리

### 7-1. 인덱스 문서 보강

현재 임베딩 문서는 다음과 같다.

```text
name + category + subcategory
```

변경 후에는 검증된 facet을 추가한다.

```text
name + category + subcategory + intents + styles + cuisines + menus + occasions
```

태그를 추가하면 기존 임계값 `0.50`의 분포가 달라질 수 있다. 기존 값을 그대로
정답으로 간주하지 않고 실데이터 평가 세트를 다시 실행해 임계값과 top-K를 정한다.

재평가는 새로 만들지 않고 있는 것을 쓴다.

```powershell
Set-Location backend
python -m scripts.seed.reset_and_seed
python -m scripts.evaluate_query_hybrid
```

- 현재 기준선은 **긍정 114 + 부정 20 = 134개 질의**다. 총점과 클래스별 수치는
  [search-eval-set.md](search-eval-set.md) 5절이 단일 출처다(여기에 복제하지 않는다).
  facet을 넣은 뒤 이 값이 떨어지면 재현율이 아니라 회귀로 본다.
- 이 점수는 이름·카테고리·소분류 패턴 일치라는 최소 지표라, `운동화 사고 싶다 → 나이키 라이즈`처럼
  사람이 보기에 맞는 결과도 실패로 센다. facet 태그가 붙으면 기대 패턴 자체를 손봐야 하므로,
  **평가 세트 수정과 임계값 재튜닝을 같은 커밋에서 하지 않는다.** 먼저 기대 패턴을 facet 기준으로
  갱신해 현재 코드로 기준선을 다시 찍고, 그다음 인덱스 텍스트를 바꾼다.
- 질의별 상위 점수 확인은 [`backend/notebooks/faiss_eval.ipynb`](../../../backend/notebooks/faiss_eval.ipynb).

FAISS.md 11-1이 재현율을 올리는 방법으로 첫 번째로 적은 것이 **임베딩 텍스트 보강**이다.
7-1은 그 항목의 실행이며, 임계값을 내려서 해결하려던 시도가 아니다(무의미 문자열 `asdfqwerzxcv`가
0.458로 유효 질의 바로 아래 붙어 있어 임계값으로는 더 못 내린다).

### 7-2. 처리 순서

1. 정확 이름·동의어 경량 검색
2. **단일 대상으로 확정 가능할 때만** `direct`
3. 질의를 검색 의도(intent)와 facet 후보로 해석
4. 검증 태그로 후보 집합 생성
5. 후보가 넓으면 구분력이 가장 큰 facet 질문 선택
6. 후보를 임베딩 관련도와 선택 facet 일치도로 정렬
7. 같은 브랜드·소분류·층·이름에 몰리지 않도록 다양성 보정
8. 최대 N개 추천과 태그 기반 이유 반환

2단계의 판단은 현재 `_is_confident_light_match`를 그대로 쓰면 안 된다. 그 함수는
tier 0·1을 무조건 확정하므로 `"명품"`(43건)·`"레스토랑"`(65건)이 3단계에 도달하지
못한다(1-4). 탐색 경로에서는 다음으로 바꾼다.

| tier | 뜻 | 현재 | 탐색 경로 |
|---|---|---|---|
| 0 | 정확 이름 일치 | 확정 | 확정 유지 — `"탠디"`는 바로 안내 |
| 1 | 카테고리·소분류 정확 일치 | 확정 | **후보가 1건일 때만 확정**, 여러 건이면 clarify 후보 집합으로 |
| 2 | 이름 부분 일치 | 최상위 그룹의 이름이 하나면 확정 | 그대로 |

tier 0도 같은 이름이 여러 층에 있으면 여러 건이지만, 이때는 대상이 하나이므로
`_is_confident_light_match`의 기존 판단(이름이 하나면 단일 대상)을 유지한다.
tier 1의 후보 수 판정에도 같은 기준을 쓴다 — 서로 다른 이름이 둘 이상이면 확정하지 않는다.

임베딩은 후보의 관련도 정렬을 돕지만, 존재하지 않는 facet을 생성하거나 검증 태그를
덮어쓰지 않는다.

7단계의 다양성 보정에는 **이름 기준 중복 제거를 반드시 포함한다.** 편의시설이 코퍼스의
67%이고 엘리베이터·에스컬레이터는 12개 층에 같은 이름으로 존재하므로(1-6), 이름 축을
빼면 상위 N이 같은 시설의 층 목록으로 채워진다.

### 7-3. 질문 선택

질문은 임의 생성하지 않고 intent별 템플릿을 사용한다.

| intent | 첫 질문 축 | 질문 예시 |
|---|---|---|
| 신발 | styles | 어떤 스타일의 신발을 찾으세요? |
| 식사 | cuisines | 어떤 종류가 좋으세요? |
| 카페 | occasions 또는 menus | 커피, 디저트, 간단한 식사 중 무엇을 찾으세요? |
| 선물 | audiences 또는 styles | 누구를 위한 선물인가요? |

현재 후보를 실제로 나누지 못하는 facet은 질문으로 선택하지 않는다. 예를 들어 모든
후보가 `일식`이면 음식 종류를 다시 묻지 않는다.

#### 되묻지 않는 조건 (구현: `_pick_question`)

세 가지를 **모두** 만족해야 질문이 된다. 하나라도 어긋나면 `results`로 간다.

| # | 조건 | 어겼을 때 생기는 화면 |
|---|---|---|
| 1 | 서로 다른 값이 둘 이상 | 후보 43건이 전부 `명품`인데 스타일을 다시 물음 |
| 2 | **그 값들이 서로 다른 후보를 가리킨다** | 아래 |
| 3 | 그 축을 가진 후보가 절반 이상 | 답하는 순간 미태깅 후보가 통째로 사라짐 |

**2번은 실기기에서 드러나 뒤늦게 추가했다(2026-08-08).** `샤낼 뷰티`를 치니
`무엇을 찾으세요? [향수 (10)] [화장품 (10)]`이 떴는데, `_intents.json`의 두 intent가
같은 규칙(`subcategory: ["화장품·향수"]`)이라 **어느 쪽을 눌러도 같은 10건**이었다.
값 개수만 세던 구현은 이 쌍을 "선택지 2개"로 통과시켰다. 고르는 행동이 아무것도 바꾸지
못하는 질문은 질문이 아니다 — 사용자에게는 "둘 중 뭘 고르라는 거지"만 남는다.

**데이터는 고치지 않는다.** 이 쌍은 임베딩 쪽에서는 의도된 것이다 — 소분류가 복합
라벨이라 `화장품`만 선언하면 문서 텍스트의 단어 빈도가 쏠려 `향수` 질의가 회귀했다
([FAISS.md 11-4](FAISS.md)). 한 데이터가 **임베딩 가중치**와 **질문 선택지**라는 두
용도를 겸하는데 두 번째 용도에서만 무효인 경우라, 질문 축으로 쓸 때만 걸러낸다.

부분적으로만 겹치는 값은 그대로 질문으로 남는다(고르면 후보가 실제로 줄어든다).
경계는 `test_discover_일부만_겹치는_값은_질문으로_남는다`가 고정한다.

**실기기에서 양방향을 확인했다(2026-08-08).**

| 질의 | 선택지 (후보 수) | 판정 |
|---|---|---|
| `샤낼 뷰티` | 향수 (10) · 화장품 (10) — 같은 집합 | 질문 없음 → `results`, 1순위가 샤넬 뷰티 |
| `신발` | 컨템포러리 (43) · 명품 (40) · 캐주얼 (37) · 스포츠 (22) · 골프 (10) | 질문 유지 |

곁다리 개선 하나 — `results`로 가면 질문 축이 근거로 실리지 않아 목록 첫 줄이 층으로
폴백된다. 예전에는 모든 행에 `화장품·향수 관련 매장이에요.`가 똑같이 반복됐는데, 같은
문구를 여섯 번 읽는 것보다 층이 유용하다.

## 8. API 계약

### 8-1. 기존 계약 보존

`POST /query/destination`은 목적지 한 건을 고르는 기존 계약을 유지한다.
정확한 매장 검색과 길찾기 내부 흐름을 추천 기능 때문에 깨지 않는다.

`POST /query/ai`는 탐색용 `DiscoveryResponse`로 분리한다. 기존 Flutter의
`searchDestinationsAi` 파서는 함께 변경해야 한다.

### 8-2. 요청안

초기 버전은 서버 대화 세션을 만들지 않는다. Flutter가 원문과 현재 선택을 매 요청에
다시 보내는 stateless 계약을 사용한다.

```json
{
  "text": "신발",
  "building_id": "thehyundai-seoul",
  "current_floor_id": "1F",
  "selected_facets": {
    "styles": ["스포츠"]
  },
  "show_all": false
}
```

`show_all`은 기본값이 `false`인 선택 필드다. clarify 화면에서 사용자가 `전체 보기`를
누르면 원문과 `selected_facets: {}`를 유지한 채 `true`로 보낸다. 서버는 같은 후보와
선택 필터를 계산하되 질문만 생략하고 `results`를 반환한다. 후보 없음(`no_match`)과
의미 검색 불가(`degraded`) 판정은 이 값으로 바꾸지 않는다.

`current_floor_id`는 후보 제거 조건이 아니라 거리·접근성 정렬 보조로만 사용한다.
현재 층에 식당이 없다는 이유로 타 층 식당 전체를 없애서는 안 된다.

**이건 현재 동작을 바꾸는 결정이다.** 지금 `match_ai_destination`은 `current_floor_id`를
1차 경량의 `_load_stores`에 **하드 필터로** 넘긴다(2차 의미 검색만 건물 전체를 본다).
`ai_search_sheet`는 현재 층을 보내므로, 계약을 "정렬 보조"로 바꾸면 그 화면의 시설 질의
동작이 달라진다. `"화장실"`처럼 층 스코프가 있어야 가까운 층이 나오는 질의를 FAISS.md
10절이 검증 항목으로 잡고 있으므로, 다음 중 하나를 명시적으로 고른다.

- (A) 탐색 경로에서도 tier 0·1 시설 질의는 층 스코프를 유지하고, facet 후보 집합에만
  정렬 보조로 쓴다. — 기존 검증 항목이 그대로 남는다. 기본안.
- (B) 전 구간 정렬 보조로 통일한다. — 계약은 단순해지지만 FAISS.md 10절의
  `current_floor_id` 관련 검증 항목을 다시 정의해야 한다.

### 8-3. 응답안

```json
{
  "mode": "clarify",
  "query": "신발",
  "source": "light",
  "question": "어떤 스타일의 신발을 찾으세요?",
  "options": [
    {"facet": "styles", "value": "스포츠", "label": "스포츠", "count": 3},
    {"facet": "styles", "value": "캐주얼", "label": "캐주얼", "count": 4},
    {"facet": "styles", "value": "구두·정장", "label": "구두·정장", "count": 2}
  ],
  "matches": [
    {
      "store_id": "PO-...",
      "name": "나이키 라이즈",
      "category": "패션",
      "subcategory": "캐주얼·스트리트",
      "floor_id": "FL-...",
      "floor_name": "B2",
      "entrance_node_id": "FL-...:ND-...",
      "centroid_local_m": {"x": 0.0, "y": 0.0},
      "centroid_wgs84": {"lat": 0.0, "lng": 0.0},
      "matched_facets": {
        "intents": ["신발"],
        "styles": ["스포츠", "캐주얼"]
      },
      "reason": "스포츠·캐주얼 신발을 찾을 때 볼 만해요."
    }
  ]
}
```

`mode`:

| mode | 의미 | 클라이언트 처리 |
|---|---|---|
| `direct` | 명확한 목적지 한 건 | 매장 카드와 길찾기 동작 표시 |
| `clarify` | 후보가 넓어 한 번 더 선택 필요 | 질문 chip + 초기 추천 표시 |
| `results` | 선택이 충분히 좁혀짐 | 추천 목록 표시 |
| `no_match` | 검증된 후보 없음 | 선택 초기화·다른 표현 안내 |
| `degraded` | 의미 모델 사용 불가, 경량/태그 결과만 제공 | 가능한 결과 표시 + 제한 안내 |

`source`는 **후보를 무엇으로 잡았는가**다. `mode`("얼마나 좁혀졌나")와 축이 다르다 —
`results`·`clarify`는 어느 경로에서도 나오므로 mode만으로는 구분할 수 없다.

| source | 의미 | 클라이언트 처리 |
|---|---|---|
| `light` | 이름·카테고리·동의어·intent — 결정적 어휘 | 온디바이스 이름 후보를 **대체한다** |
| `semantic` | FAISS 임베딩 유사도 — 추측 | 이름 후보가 있으면 **버린다** |

클라이언트가 이 값을 필요로 하는 이유와 실기기 근거는
[search-input-assist.md](../../client/search-input-assist.md) V절에 있다. 요약하면,
온디바이스 이름 후보는 임베딩에는 이겨야 하고(A.P.C.가 주차구역으로 갈아치워지던 문제)
어휘에는 져야 한다(`커피`가 카페 53곳을 못 보여주던 문제). 필드가 없는 구버전 서버에
붙으면 클라이언트는 `semantic`과 같이 취급한다 — 모르면 이름 후보를 지키는 쪽이 안전하다.

원본 `store_search_facets.json` 전체를 응답으로 보내지 않는다. 현재 질문의 option과
현재 추천 결과의 일치 facet만 보낸다.

### 8-4. `degraded`는 지금 코드로는 판별할 수 없다

`semantic_search`는 다음 세 경우를 **모두 `None`으로 돌려준다.**

1. 모델 로드 실패·미준비 (`_get_model()` → `None`)
2. 인덱스 빌드 실패 (건물에 매장이 0건 등)
3. 최상위 유사도가 `SIMILARITY_THRESHOLD` 미달

1·2는 `degraded`(제한 안내), 3은 `no_match`(다른 말로 다시)다. 사용자에게 다른 문구를
보여야 하는데 호출부가 구분할 근거가 없다. 이 구분은 `mode` 계약을 만들기 전에 해결한다.

- `semantic_search`가 `(reason, hit)`처럼 사유를 함께 돌려주거나, 모델 미가용을 별도
  조회 함수로 노출한다.
- 조건은 "예외를 삼켜 경량 경로를 살린다"는 기존 원칙을 깨지 않는 것이다. 사유만
  드러내고 예외는 그대로 삼킨다.
- `_model_load_failed`는 한 번 참이 되면 프로세스가 살아 있는 동안 재시도하지 않는다.
  `degraded`를 화면에 계속 띄우게 되므로, 재시도 정책을 함께 정한다(현재는 재기동만).

필수 UX:

- 타이핑 중 경량 결과가 없다는 이유만으로 최종 `"결과 없음"`을 표시하지 않는다.

### 9-1. 되물음 줄은 한 줄로 고정한다 (2026-08-08)

**질문·선택지·조작 버튼이 세로로 쌓여 정작 결과를 화면 밖으로 밀어냈다.** `신발`
질의에서 질문(14px 굵게) + `ActionChip` 5개가 접힌 2줄 + `전체 보기` 한 줄이 각각
자리를 차지해 세로 150px가 넘었고, 결과는 3건째부터 보이지 않았다.

바꾼 규칙은 셋이다.

1. **질문은 머리말 크기로.** 같은 패널의 `검색어 제안`·`최근 검색어`와 같은
   12px 회색이다. 되물음은 답을 좁히는 보조 수단이지 화면의 주인공이 아니다.
2. **선택지는 한 줄에서 가로로 스크롤한다.** 접지 않으므로 선택지가 몇 개든 패널
   높이가 그대로다. 세로 150px → 50px 안팎.
3. **조작 pill은 그 줄의 끝, 세로 구분선 뒤에 온다.** clarify면 선택지 줄 끝의
   `전체 보기`, 선택 뒤면 선택 줄 끝의 `전체 보기`·`다시 선택`이다. 성격이 다른 것을
   한 줄에 두되 섞이지 않게 하는 방법은
   [naver-map-ui-ux-analysis.md](../../client/naver-map-ui-ux-analysis.md) 5·6절에
   관찰돼 있던 패턴이다. 예전에는 `전체 보기`가 혼자 윗줄에 떠서, 방금 고른 선택보다
   **위에** 탈출구가 있는 순서가 됐다.

pill은 새로 만들지 않고 Runtime Kit의 `RoutexChipBar`를 카테고리 시트의 소분류 줄과 함께
쓴다. 둘은 하는 일이 같다 — "지금 보이는 목록을 이 값으로 좁혀라". 같은 일을 하는 것이
화면마다 다르게 생기면 사용자는 다른 기능으로 읽는다.

**`전체 보기`·`다시 선택`은 칩이 아니라 `RoutexButton(quiet)`이다.** 칩은 "이 값으로
좁혀라"이고 이 둘은 "좁히지 말고 다 봐라"·"방금 답을 되돌려라"라 성격이 다르다. 모양이
다르면 성격이 다르다는 것을 선으로 가르지 않아도 된다.

선택된 값은 `스포츠 선택됨` 라벨 대신 **채워진 pill + `×`** 로 바꿨다. 카테고리 시트의
소분류 pill이 이미 "고른 걸 다시 누르면 풀린다"로 동작하므로, 같은 모양이 같게 동작한다.

### 9-2. 되풀이되는 추천 이유는 행에서 뺀다 (2026-08-08)

`reason`이 **층을 통째로 대체**하고 있었고, 그 자리에 들어간 문장이 행마다 똑같았다.

```text
전:  폴리테루   신발 관련 매장이에요. 캐주얼 스타일 매장이에요.
     미우미우   신발 관련 매장이에요. 컨템포러리 스타일 매장이에요.
     몽클레르   신발 관련 매장이에요. 명품 스타일 매장이에요.

후:  폴리테루   B2 · 캐주얼 스타일 매장이에요.
     미우미우   1F · 컨템포러리 스타일 매장이에요.
     몽클레르   1F · 명품 스타일 매장이에요.
```

앞 문장은 세 행이 같고 목록 머리말(`뜻이 비슷한 매장을 찾았어요`)이 이미 말한다. 행마다
되풀이하면 정보량이 0이면서, 행마다 다른 층을 밀어낸다. **모든 행에 똑같이 들어 있는
문장만 걷어내고 층은 항상 남긴다.** 선택으로 좁혀져 근거가 전부 같아지면(`캐주얼` 선택
뒤) 문장이 통째로 사라지고 층만 남는다.

**서버 `reason`은 그대로 둔다.** 한 건만 떼어 봐도 근거가 서야 한다는 계약이고
(`test_추천_이유는_질문축과_질의_intent를_함께_말한다`), 여러 행을 함께 놓고 볼 때
무엇이 겹치는지는 **화면만 아는 사실**이다. 규칙은
[`client/lib/domain/search/reason_text.dart`](../../../client/lib/domain/search/reason_text.dart)가
단일 출처다.

구현하며 잡은 함정 둘 — **행이 하나뿐이면 공통은 없다**(비교할 상대가 없으면 되풀이도
없는데, 이걸 빼먹으면 결과가 한 건일 때 근거가 통째로 사라진다). **없던 마침표를 만들지
않는다**(`split('.')` 뒤에 마침표를 일괄로 되붙이면 마침표 없이 끝난 근거가 바뀐다).
- 선택한 facet을 chip으로 보여주고 개별 해제가 가능해야 한다.
- 추천 매장을 선택하면 기존 매장 정보·길찾기 시트로 연결한다.
- `전체 보기`, `다시 선택` 경로를 항상 제공한다.

이 중 일부는 이미 있다. 새로 만드는 것과 고치는 것을 구분해 둔다.

| 항목 | 현재 | 할 일 |
|---|---|---|
| 의미 검색 중 별도 문구 | `_searchingSemantic` → `"뜻이 비슷한 매장을 찾는 중…"` | 문구만 탐색용으로 교체 |
| 늦은 응답 방어 | `_requestId` 순번 | 유지 |
| 의미 결과 표시 구분 | `_fromSemantic` 배너 | clarify/results 표시로 확장 |
| 의미 검색 시작 조건 | `submitTick` + 경량 빈손 | debounce 종료로도 실행, 경량 결과가 있어도 실행 |
| 최종 `"결과 없음"` | `_submittedQuery`만 차면 즉시 표시 | 의미 검색 단계를 통과한 뒤에만 표시 |
| facet 선택 상태 | 없음 | 신규 |
| 상태 열거 | `_searching`·`_searchingSemantic`·`_fromSemantic` 불리언 3개 | 위 열거형으로 정리 |

불리언 세 개로 상태를 표현하는 현재 구조는 `clarify`·`results`·`degraded`가 들어오면
조합이 8가지가 된다. 상태 열거를 먼저 도입하고 화면 로직을 그 위에 얹는다.

## 11. 구현 단계

### Phase 0 — 계약을 안 바꾸고 지금 고칠 수 있는 것

facet도 새 응답 모델도 필요 없고, 넣어 두면 이후 단계의 검증이 쉬워지는 것들이다.

- 타이핑 중 경량 빈손일 때 최종 `"결과 없음"` 문구를 띄우지 않는다(1-2).
- 의미 검색을 `onSubmitted` 하나에 의존하지 않게 debounce 종료에도 태운다.
  비용은 FAISS.md가 기록한 대로 모델 로드(약 6초)가 한 번이고, `NAV_WARM_EMBEDDING=1`이
  그것을 기동 시점으로 옮긴다. 다만 첫 사용자가 워밍 전에 들어오는 경로는 남으므로
  최소 debounce 간격을 함께 정한다.
- `semantic_search`의 실패 사유 구분(8-4). `degraded` 계약보다 먼저 들어가야 한다.

완료 기준: `"신발"`을 치기만 해도(엔터 없이) 의미 검색이 돌고, 그 전에는 최종 없음
문구가 나오지 않는다.

## 12. 확정 사항과 미결정 사항

### 확정

- 기존 Studio 원본과 `category/subcategory`는 보존한다.
- 검색·추천용 수작업 원본 JSON을 별도로 둔다.
- 태그는 매장 ID 기준이고 vocabulary로 통제한다.
- `intents` 스키마는 **소분류 규칙 객체 + 예외 매장 id**로 확정한다(매장별 배열은 기각).
  선언 위치는 vocabulary가 아니라 `resources/store_search_facets/_intents.json`이고,
  시드가 규칙을 전개해 `Store.search_facets["intents"]`에 적재한 값을 검색이 사용한다.
  선언 목록·건수는 그 파일이 단일 출처다(5-1-1).
- **소분류에 없는 말만 intent로 넣는다.** 소분류가 이미 사용자 어휘와 같으면
  (`아이웨어`·`호텔`) `query_synonyms.json` 별칭으로 잇는다 — intent는 임베딩 문서
  텍스트를 바꾸므로 이름 신호를 밀어내 오타 질의가 회귀한다([FAISS.md](FAISS.md) 11-6).
- **언어 축도 같은 파일이 맡는다.** 영문 일반명사(`toilet`·`shoes`)는 별칭으로 넣고
  모델을 바꾸지 않는다 — 한국 매장명은 영어의 음차라 임베딩이 넘을 수 없고, 다국어
  모델은 어느 임계값에서도 오탐이 0이 되지 않았다([FAISS.md](FAISS.md) 11-7).
- 원본 JSON 전체를 Flutter에 보내지 않는다.
- `/query/destination`의 단일 목적지 계약은 유지한다.
- 대화형 탐색은 여러 후보·질문·선택지를 표현하는 별도 응답 모델을 사용한다.
- 초기 추천 문구는 검증 태그 기반 템플릿으로 만든다.
- 사용자 선택은 초기 버전에서 검색 세션 안에서만 유지한다.

### 미결정 — 기본 제안

| 항목 | 기본 제안 | 확정 필요 |
|---|---|---|
| 초기 추천 개수 | 최대 5개 | 사용자 선택 |
| 질문 전 초기 후보 | 질문과 함께 3개 | 사용자 선택 |
| 취향과 거리 우선순위 | 취향 적합도 우선, 현재 층은 보조 | 사용자 선택 |
| 취향 보존 기간 | 검색 패널을 닫을 때까지 | 사용자 선택 |
| 태그 입력 책임 | 수작업 검수 후 PR | 담당자 결정 |
| 음식 태그 범위 | cuisine·menu·occasion부터 | 데이터 조사 후 확정 |
| 가격대 | 초기 제외 | 근거 데이터 확보 후 결정 |
| API 전환 방식 | `/query/ai` 계약 변경 | 하위 호환이 필요하면 `/query/discovery` 신설 |
| `ai_search_sheet` 처리 | 상단 검색으로 탐색 진입점 일원화 | 시트를 남길지 결정(1-3) |
| `current_floor_id` 의미 | (A) tier 0·1 시설 질의는 층 스코프 유지 | 8-2의 A/B 선택 |
| 모델 로드 실패 재시도 | 현재대로 재기동만 | `degraded` 지속 노출 허용 여부(8-4) |
| facet 검증 범위 | facet 파일만 검증 | `store_categories.json`까지 볼지(5-0) |
| 인덱스 캐시 무효화 | 재기동 | 시드 후 자동 무효화를 넣을지(6-1) |

이 표의 미결정 항목을 확정하기 전에는 전체 매장 태깅이나 API 구현에 들어가지 않는다.
단, 11절 Phase 0은 이 표와 무관하게 먼저 진행할 수 있다.
