# 질의 경로가 안 쓰는 JSON을 읽고 있었다 (2026-08-17)

백엔드 CI가 10분 넘게 도는 이유를 재다가 찾은 것이다. 원인은 테스트가 아니라
**질의 경로 자체**였고, 고치니 테스트 스위트가 310초 → 47초가 됐다.

## 어떻게 찾았나 — 가설 셋이 다 틀렸다

이 문서를 남기는 진짜 이유는 여기다. 짐작으로 고쳤으면 엉뚱한 것을 고쳤다.

| 가설 | 반증 |
|---|---|
| 실데이터 시드가 비싸다 | `real_session_factory`가 `scope="session"` — 시드는 1회다 |
| 임베딩 모델 423MB를 매 런 내려받는다 | 로컬은 모델이 캐시돼 있는데도 같은 테스트가 238초였다 |
| 임베딩 인코딩이 비싸다 | 그 테스트가 쓰는 `match_destination`은 2차 의미 검색을 아예 부르지 않는다 |

CI 로그 타임스탬프로 구간을 재니 `test_동의어_사전은_실존_장소로_매칭된다` 하나가
파일 293초 중 **238초**였다. 그 다음은 1.57초다.

## 무엇이었나

그 테스트는 동의어 **321건 전부**에 `match_destination`을 돌린다. cProfile 결과다.

```
235.3s  전체
180.1s  json/decoder.raw_decode        ← 2,106,081회
  5.7s  _rank_with_candidate           ← 랭킹 로직 자체
```

**JSON 역직렬화가 77%였다.** 210만 = 321 질의 × 매장 1,640건 × JSON 컬럼 4개다.

컬럼 넷은 `Store.polygon`, `Store.search_facets`, `Floor.footprint_local_m`,
`Floor.non_walkable_polygons_local_m`. 이 중 질의 경로가 실제로 읽는 것은
`search_facets` 하나뿐이다 — 나머지 셋은 매장 외곽선·층 외곽선이라 **행마다 가장 큰
JSON인데 아무도 안 본다.**

## 고친 것

`query_search._load_stores`가 셋을 `defer`한다. 역직렬화가 1/4로 줄고, 남는 하나는
작다.

```python
.options(
    defer(Store.polygon),
    defer(Floor.footprint_local_m),
    defer(Floor.non_walkable_polygons_local_m),
)
```

| | 전 | 후 |
|---|---:|---:|
| `test_real_data_smoke.py` | 293초 | **14초** |
| 백엔드 전체 (684건) | 310초 | **47초** |

**이건 테스트만의 이야기가 아니다.** 같은 로드를 실제 질의 요청도 매번 한다 —
질의 하나가 매장 1,640건의 폴리곤을 읽어 버리고 있었다.

## 왜 `defer`이고 무엇을 조심하나

`defer`는 컬럼을 빼는 게 아니라 **접근할 때 다시 읽는다.** `query_search`는 셋을
쓰지 않으므로 이 경로에서는 추가 조회가 없고, 다른 경로가 같은 `Store`를 만져도
필요한 시점에 lazy로 채워진다.

그래서 위험은 하나다 — **이 모듈이 나중에 저 셋 중 하나를 읽기 시작하면**, 행마다
조회가 하나씩 붙는 N+1이 된다. 그때는 `defer`를 지우는 게 아니라 그 컬럼만
`undefer` 하거나 필요한 매장 1건에 대해서만 읽어야 한다.

## 남은 것

`--durations=15`를 `pyproject.toml`에 넣어 두었다. 이번처럼 한 테스트가 스위트를
지배하는 상황이 다시 생기면 로그에서 바로 보인다.

측정하지 않은 것도 적어 둔다. **CI 백엔드 잡의 준비 단계 1분 55초**(torch 설치 22초 ·
requirements 32초 · mypy 52초)는 손대지 않았다. 지금은 pytest보다 이쪽이 커졌으므로,
다음에 CI 시간을 줄일 일이 있으면 여기부터 본다.
