# Wave 0 — 매장 상세 사전 조사

작성일: 2026-07-30

상태: 완료 (설계 문서 9절 미결정 항목에 대한 답 포함)

상위 문서: [place-detail-interface.md](place-detail-interface.md)

설계 문서를 쓸 때 "1,640건"이라는 총량만 알고 있었다. 그 숫자로는 무엇을 만들지 정할 수
없어서, **실제로 무엇이 들어 있는지**와 **코드가 상세를 붙일 준비가 되어 있는지**를
직접 세어 봤다. 결론부터: 상세가 성립하는 매장은 **539건(32.9%)** 이고, 클라이언트는
**매장 id를 시트까지 들고 오지 못한다**. 후자가 이번 작업의 첫 번째 실제 블로커다.

## 2. 코드가 준비되어 있는가 — 블로커 3건

### B1. `PoiSearchResult`에 매장 id가 없다 ★ 최우선

상세 API는 `place_id`로 조회한다. 그런데 시트에 전달되는 모델에 id가 없다.

```dart
// client/lib/models/place/poi_search_result.dart
class PoiSearchResult {
  final String name;      // ← 1-3에서 봤듯 유일 키가 아니다
  final String floor;
  final LatLng point;
  final String? nodeId;
  final String? category;
  final String? subcategory;
}
```

id는 **상류에 이미 존재한다**. 잃어버리는 지점이 문제다.

| 진입 경로 | id 보유 | 잃는 지점 |
|---|---|---|
| 지도 폴리곤 탭 | ○ `StorePolygon.id` ([floor_plan.dart:130](../../../client/lib/models/building/floor_plan.dart)) | `PoiSearchResult` 변환 |
| 텍스트 검색 | ○ 서버 `QueryMatch.store_id` ([query.py:24](../../../backend/app/dto/query.py)) | 응답 파싱 |
| 저장한 장소 | ✗ `FavoritePlace`에 id 필드 자체가 없음 | **기기에 이미 저장된 항목은 소급 불가** |
| 카테고리 목록 시트 | ○ 매장 목록 API | 변환 |

`PoiSearchResult` 생성 지점은 **8곳**이다(indoor_map_screen, map_shell ×4,
http/mock destination repository, favorite_place, category_stores_sheet).
필드 하나를 추가하는 작업이 아니라 **id를 상류에서 시트까지 관통시키는 작업**이고, 그중
저장한 장소는 `nodeId`나 `건물+층+이름`으로만 식별되므로 **id가 null인 경로가 영구적으로
남는다**. 상세 시트는 이 경우를 반드시 처리해야 한다(→ 결정 D5).

### B2. 이미지를 표시할 수단이 없다

`client/pubspec.yaml`에 이미지 캐싱 패키지가 없고(`cached_network_image` 부재),
`Image.network` 사용처도 0건이다. `assets:`에는 mock JSON·SVG 4개뿐이다. `hero` 섹션을
실제로 그리려면 **의존성 추가 + 캐시 정책 + 이미지 호스팅**이 한꺼번에 필요하다.
이번 범위에서 감당할 크기가 아니다(→ 결정 D1).

### B3. 상세용 엔드포인트가 들어갈 자리는 깨끗하다

`buildings.py`는 URL 파싱과 404 변환만 하고 조회는 `building_queries`가 맡는 구조가
일관되게 지켜지고 있다. ETag 재검증 헬퍼(`http_cache.cache_headers` / `etag_matches`)도
이미 공용이다. **새 엔드포인트는 기존 패턴을 그대로 따르면 되고 구조 변경이 필요 없다.**
`tests/integration/test_store_api.py`가 이미 있어 테스트를 붙일 자리도 있다.

## 3. 설계 문서 9절 미결정 사항에 대한 답

> **이 절은 사전 조사 시점(2026-07-30)의 답이다.** 그 뒤 파일럿에서 실제 출처가 확보되면서
> D1·D2가 바뀌었다. **현재 유효한 결정은
> [place-detail-interface.md 9-1](place-detail-interface.md#9-1-갱신된-결정-파일럿-이후)에
> 있고**, 여기에는 당시의 근거를 남겨 둔다 — 같은 판단이 다시 올라올 때 무엇이 달라져서
> 결론이 바뀌었는지 대조하기 위해서다.

### D1. 이미지 — ~~이번 범위에서 제외한다~~ → **D1′로 갱신 (이미지 허용)**

근거: B2(수단 없음) + 저작권·호스팅 미해결. `hero` 섹션 타입은 **계약에는 남기되 서버가
절대 내려보내지 않는다**. 클라이언트 렌더러도 구현하지 않고, 모르는 섹션 타입을 건너뛰는
규칙(설계 4-2 규칙 2)으로 자연히 무시된다. 나중에 이미지가 생기면 렌더러 추가만으로 켜진다.

### D2. 영업시간 — ~~다루지 않는다~~ → **D2‴로 갱신 (전용 구조체 + 화면이 판정)**

근거: 원본에 없고(1절), 시간이 지나면 자동으로 거짓이 된다(설계 F3). "영업 중" 판정은
물론이고 정적 문구도 넣지 않는다. 대신 `notice` 섹션으로 **기간이 명시된 고지**(팝업
운영 기간 등)만 허용한다 — 기간이 지나면 검증 스크립트가 만료를 잡을 수 있기 때문이다.

> **뒤집혔다(2026-08-11).** 공식 매장 페이지라는 원본이 생겼고, 요일별 구조체 `hours`로
> 받아 **판정 문자열을 저장하지 않고 화면이 계산한다.** 위 근거 중 "원본에 없다"는 사라졌고
> "시간이 지나면 거짓이 된다"는 확인일 임계값을 넘기면 판정을 거두는 규칙으로 대응한다.
> 경위와 방어 장치는 [9-1 D2‴](place-detail-interface.md#9-1-갱신된-결정-파일럿-이후).

### D3. `facility` kind의 범위 — **위치 안내형 92건만 포함**

- **제외 (1,007건)**: 주차 787 + escalator 152 + elevator 68. 상세 시트를 아예 열지 않고
  지금의 마커/폴리곤 탭 동작만 유지한다.
- **포함 (92건)**: facility 52 + restroom 27 + 교통 7 + 락커 6. `kind: "facility"`로
  코어만 반환하고, 섹션은 좌표·층에서 **파생**한 위치 안내 한 줄만 붙인다(사람이 쓰지 않는다).

이 결정으로 사람이 손으로 써야 할 대상이 1,640건 → **539건**으로 줄고, 우선순위 상위 3개
층(B1·3F·4F)만 하면 **291건**이다.

### D4. 건물 홈 진입점 — **뒤로 미루고, 그때 `PlaceDetailSheet`로 대체한다**

현재는 야외에서 건물을 고르면 `_placeInfo`에 제목/부제만 세팅된다
([map_shell_screen.dart:263](../../../client/lib/screens/map_shell/map_shell_screen.dart)).
매장 상세 렌더러가 먼저 서고 나서 같은 렌더러에 `kind: "building"`을 태우는 편이,
건물용 화면을 따로 만들었다가 합치는 것보다 싸다.

### D5. id가 없는 진입 경로(저장한 장소) — **코어만 렌더한다**

`FavoritePlace`에 `placeId`를 추가해도 **이미 기기에 저장된 항목은 null**이다. 마이그레이션
(이름+층으로 재조회해 id 채우기)은 1-3의 이름 중복 때문에 안전하지 않다. 따라서 상세 시트는
`placeId == null`이면 **상세 요청 자체를 하지 않고** 코어(이름·층·카테고리·출발/도착)만
그린다. 설계 F1의 "없는 것을 없다고 말하지 않는다"와 같은 처리라 별도 UI가 필요 없다.

## 4. 이 조사가 설계 문서에 남기는 정정

1. **1-3절**: "분류조차 대부분 미분류" → 원본 파일 기준으로는 맞지만 오버레이 적용 후
   런타임에서는 미분류 0건이다.
2. **5-3절 커버리지**: "앵커 수십 건"이라는 막연한 표현 → **539건이 전체 모집단이고,
   B1·3F·4F 291건이 1차 목표**로 구체화한다.
3. **새 실패 조건 F8**: 클라이언트가 매장 id를 시트까지 전달하지 못한다(B1). 이것을
   해결하지 않으면 나머지 Wave가 전부 막힌다 — 그래서 Wave 1에서 가장 먼저 처리한다.
