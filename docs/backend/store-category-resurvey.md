# 매장 카테고리 전수 재조사 (2026-08-17)

카테고리 대분류를 **공식 층별안내**를 근거로 다시 만들었다. 이 문서는 왜 그렇게 했고,
무엇을 버렸고, 무엇이 아직 덮이지 않았는지를 적는다. 값 자체의 단일 출처는
`backend/resources/category_section_map.json`이고 여기에 값을 베껴 두지 않는다.

## 무엇이 문제였나

두 가지가 같이 보고됐다.

1. **카테고리 정렬이 이상하다.** `sortedCategoryLabels`가 순수 가나다순이라
   `리빙 → 뷰티 → 서비스 → 식품관 → 음식점 → 카페 → 키즈 → 패션 → 편의시설`이 됐다.
   매장 233개인 패션이 끝에서 두 번째, 33개인 뷰티가 두 번째였다.
2. **매장이 아닌데 `서비스`에 들어간 매장이 있다.** 실제로 `서비스` 23건 중 절반 이상이
   리테일이거나 식당이었다 — 삼성스토어(가전 매장), SMT 라운지(6F 전문식당가),
   더현대 수비니어·ATTAG·두두두 쇼룸(리테일).

원인은 같다. **분류의 근거가 없었다.** Studio 원본(다베오)은 리테일을 전부
`category="매장"`으로 뭉개서 넘겨주고, 그걸 사람이 브랜드명만 보고 손으로 채운 매핑이
`store_category_by_name.json`이었다. 이름만으로 판정하니 "라운지"가 들어간 식당이
서비스가 되고, "바로서비스"가 붙은 가전 매장이 서비스가 됐다.

## 원본을 어디서 가져왔나

더현대 서울 공식 사이트의 층별안내가 JSON API로 열려 있다.

```
https://thehyundaiseoul.ehyundai.com/api/floor-brands?floorCode={code}&locale=ko
B2=B010B200  B1=B010B100  1F~6F=B0100100 … B0100600
```

8개 층 · 43개 섹션 · 매장 536개. 각 매장에 공식 대분류(섹션명)·전화·`brandCode`가 붙어
있다. 응답을 그대로 합친 스냅샷이 `backend/resources/official_floor_guide.json`이다.

> **HTML을 긁으면 안 된다.** 초기 HTML에는 매장이 한 건도 없다(Next.js가 클라이언트에서
> 위 API를 부른다). 페이지를 fetch해서 파싱하는 방식은 조용히 빈 결과를 준다.

재수집은 브라우저 없이 된다.

```powershell
$codes = @{'1F'='B0100100';'2F'='B0100200';'3F'='B0100300';'4F'='B0100400';
           '5F'='B0100500';'6F'='B0100600';'B1'='B010B100';'B2'='B010B200'}
foreach ($k in $codes.Keys) {
  Invoke-WebRequest -UseBasicParsing -OutFile "$k.json" `
    "https://thehyundaiseoul.ehyundai.com/api/floor-brands?floorCode=$($codes[$k])&locale=ko"
}
```

`-OutFile`을 쓴다. `$r.Content`로 받아 다시 쓰면 PowerShell이 latin-1로 디코딩해
한글이 깨진다.

## 왜 공식 섹션을 그대로 쓰지 않았나

**섹션은 층별 MD 구획이지 카테고리가 아니다.** `카페 · 베이커리 · 디저트`가 B1·3F·4F·6F에
각각 따로 있고, 이름이 같아도 층이 다르면 다른 섹션이다. 43개를 그대로 chip으로 늘어놓으면
UI가 못 버티고, 무엇보다 우리 앱이 답하려는 질문("이 건물 어디에 카페가 있나")과 축이
다르다. 공식은 "4층에 무엇이 있나"를 답한다.

그래서 **섹션 → 우리 대분류 매핑표**를 두고 자동 생성한다. 근거가 매장마다
"공식이 이 섹션에 넣었다" 한 줄로 고정되고, 규칙이 43줄이라 사람이 눈으로 검토할 수 있다.

버린 대안 하나 더 — **매장을 하나씩 다시 판정하기.** 정확도는 가장 높아 보이지만 지금
틀린 데이터가 정확히 그 방법으로 만들어졌다. 근거가 "판단"이라 리뷰도 재현도 안 되고,
원본이 바뀌면 처음부터 다시 해야 한다.

## 섹션 매핑만으로는 조용히 틀리는 자리

이 재조사에서 가장 중요한 부분이다. **섹션 단위 1:1 매핑은 섞인 섹션에서 오류를 균일하게
퍼뜨린다.**

| 섹션 | 섞여 있는 것 |
|---|---|
| 6F `기타 · 편의시설` | 두두두 쇼룸(아트토이 리테일) + ATM + 흡연실 + ALT.1(전시장) |
| 1F·5F `컬쳐&공간` | 작가 작품 + 정원 + 더현대 수비니어(리테일) + 디즈니스토어 |
| B2 `컬쳐 · 라이프스타일` | 마뗑킴(패션) + 포인트 오브 뷰(문구) + LISTENING ROOM(음향) |
| B1·6F `편의시설` | 수유실·물품보관함 + 카페 H(카페) |
| B2·5F `F&B` | 스타벅스(카페) + 번패티번(식당) |
| B1 `차 · 건강` | 정관장(식품) + 오설록(카페) |

그래서 `category_section_map.json`에 `storeOverrides`를 두고 **매장 단위로만** 이긴다.
섹션 규칙이 맞는데 소분류만 뭉개지는 자리도 여기서 되돌린다 — 1F `럭셔리부띠끄`에
티파니앤코·불가리가 같이 있어 전부 `명품`이 되면 시계를 찾는 사람이 pill로 좁힐 수 없다.

## 소분류는 검색이 붙잡고 있다 — 뭉치면 검색이 깨진다

**이 재조사에서 가장 비싸게 배운 것이다.** 처음에는 "검색 패싯은 store_id 기준이라
카테고리를 바꿔도 영향이 없다"고 보고 넘어갔는데, CI가 86건을 떨어뜨렸다.
`store_search_facets/_intents.json`의 intent는 **소분류를 직접 규칙으로 건다.**

```json
"고객센터": { "rules": { "subcategory": ["고객서비스"] } }
"꽃":      { "rules": { "subcategory": ["플라워"] } }
```

소분류를 없애면 그 intent가 잡을 것이 사라지고, 시드가 리소스 검증에서 죽는다.
실제로 깨진 자리는 넷이었다.

| 무엇 | 왜 |
|---|---|
| `고객서비스` 소멸 | 고객 응대 창구를 `생활편의`로 뭉갰다. **되살렸다** — 상담·환불·배송 데스크는 정수기·흡연실과 성격이 다르다 |
| `플라워` 소멸 | 르플로럼을 `가구·인테리어`로 옮겼다. Studio 원본이 이미 `플라워`였고 그쪽이 정확하다 |
| `가방`의 죽은 제외 | 케이스티파이가 `잡화·액세서리`를 벗어나 제외 규칙이 무의미해졌다. 폰케이스는 잡화가 맞아 되돌렸다 |
| `신발`의 중복 extra | 버윅·아떼바네사브루노·쿠에른이 공식 `슈즈&백 갤러리` 덕에 규칙에 자연히 잡혔다. **extra 목록에서 뺐다** — 재분류가 손으로 적어 둔 예외를 없애 준 자리다 |

**그래서 소분류를 합칠 때는 `_intents.json`을 먼저 본다.** 대분류만 보고 "소분류는
아무래도 좋다"고 판단하면 검색이 조용히 좁아지거나 시드가 죽는다.

## 서비스 대분류를 없앴다

`서비스`와 `편의시설`의 경계가 애초에 정의된 적이 없다는 것이 오분류의 뿌리였다.
**공식에도 `서비스`라는 대분류는 없다** — `편의시설`, `기타 · 편의시설`, `VIP 서비스`뿐이다.

없애고 행선지를 나눴다.

- 고객상담실·교환/환불·배송접수·약국·라운지·수유실 → `편의시설`
- 작가 작품·워터폴가든·사운즈포레스트·ALT.1·CH 1985 → `편의시설 / 문화·예술`
- 더현대 수비니어·ATTAG·두두두 쇼룸·삼성스토어 → 각자 리테일 대분류
- SMT 라운지 → `음식점`
- 애브뉴준오(헤어숍) → `뷰티 / 뷰티살롱`

결과는 **대분류 8개**다. 소분류에 `문화·예술`·`의료·약국`·`펫`·`뷰티살롱`이 새로 들어왔다.

## 정렬을 "카테고리로 찾는 빈도" 순으로 바꿨다

`음식점 · 카페 · 패션 · 뷰티 · 식품관 · 키즈 · 리빙 · 편의시설`.
순서표는 `client/lib/domain/category/category_label_order.dart`의
`kCategoryDisplayOrder`가 단일 출처다.

**매장 수와 순서가 다르다.** 검색 평가 세트(`backend/scripts/eval/query_eval_set.json`)
114건의 `label`을 우리 대분류로 묶으면 이렇게 나온다.

| 대분류 | 질의 | 매장 |
|---|---:|---:|
| 편의시설 | 28 | 1,125 |
| 음식점 | 16 | 59 |
| 패션 | 14 | 262 |
| 카페 | 10 | 46 |
| 식품관 | 7 | 28 |
| 리빙 | 7 | 53 |
| 뷰티 | 5 | 32 |
| 키즈 | 4 | 22 |

(나머지 23건은 상호명·오타·영어 질의라 카테고리 축이 없다.)

패션은 매장이 262개로 압도적인데 질의는 14건이다. **브랜드명을 아는 매장은 이름으로
찾고, 모르는 것만 카테고리로 찾는다.** 그래서 매장 수 내림차순은 버렸다 — 화면 순서가
"어디에 많은가"가 아니라 "무엇을 못 찾는가"를 따라야 한다. 순서를 계산하지 않고 표로
박아 두는 이유는 따로 있다. **매장 수는 재분류할 때마다 바뀌어 chip 위치가 같이 움직인다**
— 이번 재조사만으로도 대분류 순위가 여러 칸 뒤집혔다.

> chip 목록은 `getCategoryCounts(buildingId)`라 **건물 단위**다. 층을 바꿔도 chip
> 구성은 그대로고, `음식점`을 눌렀을 때 나오는 목록도 전 층을 훑는다. "식당가가 B1·6F에
> 있으니 3F에서는 첫 chip이 헛돈다"는 걱정은 성립하지 않는다.

> **이 표를 순위표로 읽지 말 것.** 평가 세트는 자연 분포가 아니라 **클래스별 할당량으로
> 설계된 테스트 세트**다(`facility` 23건은 설계값이다 — [세트 설계](native/search-eval-set.md) 3-1).
> 믿을 수 있는 것은 "시설·끼니가 쇼핑보다 위"라는 **방향**이고, 1위와 2위의 간격은 아니다.
> 진짜 순위는 chip 탭 로그를 쌓아야 나온다.

**질의가 가장 많은 `편의시설`을 맨 뒤에 둔 이유**는 두 가지다. 화장실·엘리베이터·출구는
이미 지도에 아이콘으로 그려져 chip 없이 보이고, chip을 누르면 주차 787건이 따라온다.
질의가 많은 것은 사실이지만 **그 질의가 chip으로 해결되지 않는다.**

순서표에 없는 값은 뒤에 가나다로 붙는다 — 배포 시차로 백엔드가 아직 `서비스`·`식음료`를
주는 동안에도 chip이 사라지면 안 되기 때문이다.

## 재생성 방법

```bash
cd backend
python scripts/transform/build_store_categories.py
```

`official_floor_guide.json` + `category_section_map.json` →
`store_category_by_name.json`을 다시 쓰고, **`store_categories.json`(id 맵)도 같은 값으로
맞춘다.** id 맵이 시드에서 먼저 적용되므로(`studio_adapter._resolved_category`) 여기 남은
옛 값은 새 매핑을 조용히 이긴다 — 실제로 `생로랑`이 뷰티로, `페어몬트 호텔`이 서비스로
남아 있었다.

매핑표에 없는 섹션이 나오면 스크립트가 **실패한다.** 새 섹션이 생겼는데 조용히 빠지면
그 층 매장이 통째로 Studio 원본 카테고리로 떨어지기 때문이다.

## 아직 덮이지 않은 것

**공식에 있는데 우리 도면에 없는 매장 28건.** 도면 원본(다베오 v182.8)이 공식보다 오래됐다.
`오픈 준비중` 3건을 빼면 신규 개점이거나(킬리안 파리·캐나다구스·모드나인·쿠자) 도면이
누락한 것이다. 목록은 스크립트를 돌리면 매번 출력된다.

**도면에만 있는 매장.** 1,640개 중 공식과 이름이 맞는 것은 513개다. 나머지는 대부분
시설물(주차 787·에스컬레이터 152·엘리베이터 68)이라 문제가 없지만, 그 안에 리테일이
섞여 있다 — `긴자 바이린`·`요즘김밥`·`토나리우동`처럼 공식 목록에 없는 B1 식당,
`시리즈 코너`·`비비안/ 바바라/ 피앳유즈`처럼 도면이 여러 브랜드를 한 폴리곤으로 묶은 것.
**이들은 공식으로 검증할 수 없고 기존 값을 그대로 유지한다.** 손대려면 근거가 따로 필요하다.

**이름이 달라 못 맞춘 것은 `aliases`에 적는다.** 비슷하다는 이유만으로 넣으면 안 된다 —
공식 `보스`(Bose 음향)와 도면 `보스 골프`(BOSS)는 다른 매장이고, 문자열 유사도만 보면
이어 붙게 된다.

## 검증 기준

| 무엇 | 어디서 확인 |
|---|---|
| 매핑표가 공식 섹션을 전부 덮는다 | `build_store_categories.py`가 미덮음 섹션에서 실패 |
| alias가 가리키는 도면 이름이 실제로 있다 | 같은 스크립트의 `aliasMissing` 경고 |
| 재생성 후 `서비스` 잔존 0건 | `backend/tests/unit/transform/test_build_store_categories.py` |
| id 맵과 이름 맵이 어긋나지 않는다 | 같은 테스트 |
| 저장된 파일이 지금 매핑표의 산출물과 같다 | 같은 테스트 (매핑표만 고치고 안 돌린 것을 잡는다) |
| 소분류를 바꿔도 검색 intent가 성립한다 | `tests/unit/graph/test_studio_adapter_edges.py::test_배포된_facet_리소스는_검증을_통과한다` |
| chip 순서가 고정 순서와 같다 | `client/test/domain/category/category_label_order_test.dart` |

**같은 이름이 여러 섹션에 있으면 뒤 섹션이 이긴다.** 값이 층 순서에 따라 조용히
정해지는 자리라 스크립트가 매번 목록을 찍는다. 지금 4건이고 셋은 어느 쪽이든 같은
대분류지만, `POP-UP STUDIO`는 B1 푸드스트리트와 2F 패션잡화에 함께 있어 갈린다 —
팝업은 내용이 바뀌므로 고정하지 않고 보이게만 뒀다.
