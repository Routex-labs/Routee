# 검색 입력 보조 — 자동완성·오타 교정·거리순 정렬

네이버지도·카카오맵의 검색이 자연어에 강한 이유를 뜯어보고, 그중 **입력단(사용자가
글자를 치는 동안)** 에 해당하는 개선 항목을 정리한다.

- [네이버지도 UI/UX 분석](naver-map-ui-ux-analysis.md)이 **정보 구조와 목록·시트 UX**
  (항목 A~J)를 다룬다면, 이 문서는 **매칭 품질과 입력 보조**를 다룬다. 항목 번호는
  겹치지 않게 **K부터** 이어 붙인다.
- **입력이 끝난 뒤 사용자가 고르는 목록**(후보 행의 거리·정렬·개수 표기)은
  [검색 결과 목록 UX](search-result-list-ux.md)가 **O~R**로 이어받는다. 이 문서가 만든
  후보 목록이 사실상 결과 화면으로도 쓰인다는 사실이 그 문서의 출발점이다.
- 매칭 파이프라인의 설계 근거는 [query.md](https://github.com/Routex-labs/fastapi/blob/main/docs/native/query.md) ·
  [FAISS.md](https://github.com/Routex-labs/fastapi/blob/main/docs/native/FAISS.md) · [KIWI.md](https://github.com/Routex-labs/fastapi/blob/main/docs/native/KIWI.md)가 단일
  출처다. 이 문서는 그 위에 무엇을 얹을지만 적는다.
- 정상 동작보다 **실패 조건을 먼저** 적고, **무엇이 충족되면 맞다고 볼지**를 함께 적는다
  (AGENTS.md 규칙).

## 왜 지금 임베딩이 아니라 입력단인가

FAISS 임계값·인덱스 문서를 세 번 재평가했는데 총점이 움직이지 않았다.

| 회차 | 한 일 | 결과 |
|---|---|---|
| W7 (2026-07-30) | 인덱스 문서에 `styles`·`cuisines` facet 추가 (258건) | 23/29 → **23/29** |
| W8 (2026-07-31) | `intents` 축 추가 (210건) | 23/29 → **23/29** |
| W9 (2026-08-01) | intent 2개 → 7개, 태깅 368건으로 확대 | 23/29 → **23/29** |

유효 최하단(ATM 0.464)과 무의미 질의(`asdfqwerzxcv` 0.458)의 **마진 0.006도 세 번 내내
불변**이다([FAISS.md 11-1](https://github.com/Routex-labs/fastapi/blob/main/docs/native/FAISS.md)). 세 번 손대서 안 움직였다는 건
"모델·임계값을 네 번째로 만져도 안 오른다"는 신호로 읽는다.

**네이버·카카오가 잘 하는 건 모델이 아니다.** 두 가지다.

1. **입력이 애매해지기 전에 잡는다.** 1글자부터 자동완성이 뜨고 오타가 교정된다.
   사용자가 애매한 문자열을 완성해서 엔터를 치는 일 자체가 드물다.
2. **매칭할 텍스트가 많다.** "분위기 좋은 카페"가 잡히는 건 임베딩이 좋아서가 아니라
   리뷰·블로그 텍스트가 쌓여 있어서다. 우리에겐 UGC가 없다.

우리는 2번을 단기간에 못 만든다(→ N 항목). 그러나 **1번은 지금 없고, 매장이 1640건으로
고정돼 있어 만들기 쉽다.** 그래서 다음 투자는 여기다.

> **네이버는 되묻지 않는다.** [naver-map-ui-ux-analysis.md](naver-map-ui-ux-analysis.md)
> 「2. 검색어 입력 중」에 이미 적혀 있다 — *"후보가 넓을 때 되묻지 않는다. 질문 대신
> 제안 3줄을 얹고 끝낸다."* 관찰만 남고 작업 항목이 되지 않았다. 우리 `clarify`
> (질문 → chip 선택 → 결과)는 탭을 한 번 더 요구한다. **clarify를 걷어내자는 게
> 아니라**, 자동완성이 들어가면 clarify까지 흘러가는 질의 자체가 줄어든다. 줄어든
> 뒤에 clarify를 다시 평가한다.

## K. 자동완성 (검색어 제안)

### 문제

`search_panel.dart`에 입력을 돕는 코드가 없다. 사용자는 상호를 정확히 기억해서 치거나,
틀리면 `no_match`를 받는다. 그 부담이 전부 뒤쪽 FAISS 임계값 조정으로 떠넘겨져 있다.

### 제안

매장 목록을 **앱에서 1회 받아 온디바이스로** 후보를 만든다.

```
사용자 입력: "ㄴㅇ"        → 나이키 라이즈 · 3F      (초성)
사용자 입력: "나이"        → 나이키 라이즈 · 3F      (prefix)
사용자 입력: "라이즈"      → 나이키 라이즈 · 3F      (부분 일치)
```

- 원본은 **자동완성 전용 경량 엔드포인트**를 신설한다. 기존
  `GET /buildings/{id}/stores`는 쓸 수 없다 — 아래 측정 참조.
- 한글은 **초성 검색**까지 지원한다. `ㄴㅇㅋ` → 나이키. 한국 앱에서 사실상 기본 기대치다.
- 매칭 구간 하이라이트는 **이미 구현된 `highlightedNameSpans`**(A-1)를 재사용한다.

**왜 서버 호출이 아니라 온디바이스인가.** 실내 매장 집합은 고정이고 작다(1640건).
타이핑마다 왕복하면 지연이 그대로 체감되는데, 얻는 건 없다. 네이버가 서버를 쓰는 건
전국 POI가 수천만 건이라서다. 우리 조건이 다르다.

### 실패 조건 (먼저 정한 것)

- **IME 조합 중 상태.** `ㅅ` → `사` → `샤` 로 글자가 완성되는 동안에도 후보를 갱신할지.
  → **갱신한다.** 조합 중 자모(`ㅅ`)는 초성 매칭으로, 완성 글자(`샤`)는 일반 매칭으로
  받는다. 갱신을 막으면 초성 검색이 아예 동작하지 않는다.
- **응답 크기 — 측정했고, 기존 엔드포인트는 탈락했다.**
  `StoreResponse`(`dto/floor_map.py:30`)는 **`polygon_local_m`과 `polygon_wgs84`를
  둘 다 싣는다.** 매장 1640건에 폴리곤 점이 7398개이므로, 응답에는 같은 폴리곤이
  좌표계 두 벌로 14,796점 들어간다.

  | 항목 | 비압축 | gzip |
  |---|---|---|
  | `GET /buildings/{id}/stores` (기존) | 1,258,677B (1,229KiB) | 254,748B (249KiB) |
  | └ 폴리곤 2벌 몫 | 670,402B (655KiB) | — |
  | └ 나머지 필드 몫(id·이름·카테고리·중심점·입구) | 588,275B (574KiB) | — |
  | **`GET /buildings/{id}/store-index` (신설)** | **341,135B (333KiB)** | **44,914B (44KiB)** |
  | 감소율 | **73%** | **82%** |

  자동완성에 필요한 건 이름·층·카테고리·`entrance_node_id`뿐인데 폴리곤이 전체의
  절반을 넘는다. 그래서 **경량 엔드포인트를 신설했다** —
  `GET /buildings/{building_id}/store-index`(`routers/buildings.py`).
  1.2MB짜리 JSON을 기기에서 파싱할 이유가 없다.

  > **실측 방법.** 실데이터(`resources/studio/thehyundai-seoul-dabeeo`, 매장 1640건)를
  > 임시 SQLite에 시드한 뒤 `fastapi.testclient`로 두 엔드포인트를 호출해 응답 본문
  > 바이트를 쟀다(2026-08-08). gzip 값은 서버 `GZipMiddleware`와 같은 압축 레벨 9 기준
  > 이다. 이전 판의 "약 1MB / 약 200KB"는 시드 원본에서 계산한 추정이었고, 이 표는
  > 실제 응답 실측으로 대체한 값이다.

  **좌표는 넣지 않았다.** 후보 목록은 이름과 층 라벨만 그리므로 중심점이 필요 없고,
  후보를 탭한 뒤 필요해지는 좌표는 이미 층 지도 응답(`centroid_local_m`)이나
  상세 `/places/{id}`(`position_local_m`)에서 1건만 가져올 수 있다. 인덱스에 중심점을
  얹으면 실측 +82KB(`centroid_local_m`만)·+194KB(`centroid_wgs84`까지)로 333KB가
  최대 1.6배가 된다.
- **로드 실패·지연.** 목록을 못 받으면 자동완성만 조용히 꺼지고, 기존 검색은 그대로
  동작해야 한다. 자동완성이 검색을 막아서는 안 된다.
- **구두점 상호.** `A.P.C.`·`마리떼프랑소와저버/LMC` 는 `.`·`/`를 지우면 안 된다.
  질의 쪽만 정규화하고 원본 상호는 보존한다(query.md 4절과 같은 원칙).
- **후보 개수 상한.** `ㄱ` 한 글자면 수백 건이 걸린다. 상한 없이 그리면 패널이 폭발한다.
- **중복 이름.** 화장실·엘리베이터는 층마다 있어 같은 이름이 12건씩 나온다
  (conversational-discovery 1-6절이 지적한 것과 같은 문제). 이름 축으로 묶는다.

#### 실측 — 1640건 전체에서 후보 순위 (2026-08-08)

B2 매장 이름 앞 20건을 대상으로, 이름의 앞 1·2·3글자를 차례로 넣어 그 매장이 후보
목록에서 몇 위에 오는지 쟀다. 원본은 시드 리소스
(`resources/studio/thehyundai-seoul-dabeeo/stores_*.json`(Routex-labs/fastapi), 12개 층 1640건)이며,
`suggestStores()`를 그대로 호출했다.

**20/20 통과.** 눈여겨볼 점 둘.

| 질의 | 1글자 | 2글자 | 3글자 | 비고 |
|---|---|---|---|---|
| `트리밍버드` | 1 | 1 | 1 | 흔한 경우 — 1글자에 이미 1위 |
| `MLB` | 2 | 1 | 1 | |
| `노스페이스 화이트 라벨` | 6 | 2 | 2 | 같은 브랜드 다른 매장이 1위. 3위 안이라 통과 |
| `나이스웨더` | 7 | 3 | 1 | `나`로 시작하는 매장이 많아 1글자에서는 밀린다 |
| `29CM HOME` | **권외** | 1 | 1 | `2`로 시작하는 매장이 상한 8을 넘겨 1글자에서는 안 보인다 |
| `아디다스 스타디움` | **권외** | 1 | 1 | `아`도 같은 이유 |

**1글자에서 권외로 밀리는 경우가 있고, 그게 정상이다.** 후보 상한이 8이라 `아`·`2`처럼
시작 글자가 흔하면 자리가 모자란다. 검증 기준을 "1글자"가 아니라 **"3글자 안에"** 로
잡은 이유가 이것이다 — 두 글자만 쳐도 전부 1~3위로 들어온다.

측정 스크립트는 일회성이라 남기지 않았다. 재현하려면 `suggestStores()`에 위 리소스를
읽어 넣고 같은 절차를 돌린다. 순위 로직 자체의 회귀는 실제 매장명 59건 fixture를 쓰는
`store_suggestions_test.dart`가 지킨다.

#### 구현하며 정한 것 — `domain/search/store_suggestions.dart`의 규칙

여기 적힌 것이 코드의 단일 출처다. 함수 주석에는 계약만 두고 근거는 이쪽을 본다.

**우선순위.** `SuggestionKind` 선언 순서 → (부분 일치면) 일치 시작 위치가 앞선 것 →
이름이 짧은 것 → 입력 순서. 이름 길이를 넣는 이유는 `타임`을 쳤을 때 `타임`이
`타임파리`보다 위에 와야 하기 때문이다. 마지막 입력 순서 기준은 장식이 아니다 —
**Dart의 `List.sort`는 안정 정렬이 아니라서**, 동점을 명시적으로 깨 두지 않으면 같은
입력에 대해 호출할 때마다 순서가 달라질 수 있다.

**정규화는 양쪽에 건다.** 위 「실패 조건」은 "질의 쪽만 정규화"라고 적었는데, 그것만으로는
`apc`가 `A.P.C.`를 못 찾는다. 질의와 이름 **양쪽의 매칭용 사본**에서 소문자로 낮추고
공백·구두점을 지운다. **원본 이름은 그대로 두므로** 화면에는 `A.P.C.`가 찍힌다 — 지워지는
건 표시에 쓰지 않는 매칭 키뿐이라 원칙은 지켜진다.

**중복 이름은 묶되 대표를 고르지 않는다.** 정규화한 이름을 키로 한 줄로 내보내되 묶인
매장은 하나도 버리지 않고 전부 담는다(표기만 다른 `물품 보관함`·`물품보관함`도 같이
묶인다). 어느 매장의 층을 화면에 적을지는 **거리를 아는 쪽만** 정할 수 있다(O절).

**IME 조합 중 자모 처리.**

- 질의가 **전부 자음 낱자**면(`ㅅ`·`ㄴㅇㅋ`) 초성 매칭만 한다.
- 그 밖에는 자모열 접두사로 비교한다. 조합 중간 상태(`나이`+`ㅋ` → `나잌`)는 자모로 펴면
  `ㄴㅏㅇㅣㅋ`이 되어 `나이키`(`ㄴㅏㅇㅣㅋㅣ`)의 접두사가 된다. 음절 단위로 비교했다면
  `나잌`은 아무것도 못 찾는다.

**왜 자음 낱자 질의에서 자모 접두사 비교를 아예 끄나.** `ㄱ`의 자모열은 `ㄱ` 한 자라
`가니`(`ㄱㅏㄴㅣ`)의 접두사이기도 하다. 두 경로를 다 열면 같은 결과가 `prefix`로도
`initials`로도 분류돼 "왜 후보인가"가 흔들리고, 게다가 이름 가운데 아무 `ㄱ` 음절에나
붙어 부분 일치가 폭발한다.

**초성은 이름 앞에서부터만 맞춘다.** `ㄹㅇㅈ`로 `나이키 라이즈`를 찾는 단어 경계 매칭은
넣지 않았다. 1글자 초성이 단어마다 걸리면 상한 8건이 즉시 무의미해진다. 뒷단어는
`라이즈`처럼 글자로 치면 부분 일치로 잡힌다.

## L. 오타 교정 (자모 편집거리)

### 문제

`샤낼` → 샤넬이 안 된다. 이건 **의미 문제가 아니라 표기 문제**라 임베딩이 원리적으로
못 잡는다. [search-qa-fix-wave.md](https://github.com/Routex-labs/fastapi/blob/main/docs/native/search-qa-fix-wave.md) Wave 4에
"`샤낼` 원인 추적 — Opus, 경유 지점 미확인 상태의 탐정 작업"으로 남아 있는데, 추적할
것도 없다. **교정 기능이 아예 없다.**

### 제안

한글을 초·중·종성으로 분해한 뒤 편집거리를 잰다.

```
샤낼 → [ㅅㅑ][ㄴㅐㄹ]
샤넬 → [ㅅㅑ][ㄴㅔㄹ]     자모 편집거리 1 → 후보
```

음절 단위로 재면 `낼`과 `넬`이 완전히 다른 글자라 거리 1이 안 나온다. **자모 단위로
분해해야** 한글 오타(모음 하나 차이)가 잡힌다.

- K의 후보 산출 **뒤에** 붙는다. 정확·부분 일치 후보가 있으면 교정을 시도하지 않는다.
- 서버가 아니라 클라이언트에 둔다 — K와 같은 로컬 목록을 쓰므로 왕복이 없다.

### 실패 조건 (먼저 정한 것)

- **짧은 질의.** 2글자 이하에서 편집거리 1을 허용하면 후보가 수십 건이 된다.
  → **3글자 미만은 교정하지 않는다.** query.md의 `"이"` → 이솝 케이스(Wave 4에서 이미
  한 번 다친 곳)를 다시 깨뜨리지 않기 위한 하한이다.
- **정상 질의 회귀.** 교정이 붙어서 지금 잘 되던 검색이 다른 매장으로 바뀌면 순손실이다.
  기존 결과가 있으면 교정 후보를 **아래에 덧붙이기만** 하고 순서를 바꾸지 않는다.
- **거리 임계.** 편집거리 2까지 열면 `크록스`↔`크록시` 같은 오검출이 늘어난다.
  → 기본 **1**. 넓히려면 측정 결과를 근거로.
- **영문 상호.** 자모 분해가 안 되는 라틴 문자는 일반 편집거리로 따로 처리한다.

### 검증 기준

- [x] 실제 오타 사례 20건 목록을 만들고 교정률을 기록 — `store_suggestions_test.dart`의
      fixture가 그 목록이다(ㅐ/ㅔ 혼동·된소리 누락·과잉·ㅓ/ㅏ·받침 ㄴ/ㅇ + 라틴 2건).
      **20/20**이며, fixture 59건뿐 아니라 전체 659개 상호에 대해서도 같은 결과다.
- [x] **기존 정상 질의 회귀 0건** — `이`→이솝이 교정 없이 prefix 1순위, `MLB`·`화장실` 유지
- [x] 2글자 질의에서 교정이 동작하지 않음 — `구지`가 아무 후보도 만들지 않는다
- [x] 교정 후보임이 화면에 드러남 — 후보 아이콘이 돋보기 대신 `auto_fix_high`이고,
      못 찾은 뒤 화면은 머리말이 `이걸 찾으셨나요?`로 바뀐다

#### 확정 — 교정 하한 3글자를 유지했고, 그래서 `샤낼`은 교정되지 않는다

위 「실패 조건」의 3글자 하한을 그대로 뒀다. **그 결과 이 절의 대표 예시인 `샤낼`

## M. 결과를 보행 거리순으로 정렬

### 문제

네이버·카카오의 "가까운 순"은 **직선거리**다. 실내에서 직선거리는 자주 거짓말을 한다 —
벽 하나 사이로 10m인 매장이 실제로는 반대편 에스컬레이터를 돌아 120m일 수 있다.

우리는 온디바이스 Dijkstra가 있고, **거리 계산은 이미 끝나 있다.** A-2에서
[`reachableFrom`](../../client/lib/domain/route/dijkstra.dart)을 한 번만 돌려 전 노드 결과를
받아 두고, `SearchPanel`이 `widget.reachByNodeId`로 조회한다(`search_panel.dart:817`).
**그 값을 표시에만 쓰고 정렬에는 안 쓰고 있다.**

### 제안

결과 목록을 `reachByNodeId[nodeId].distanceM` 오름차순으로 정렬한다. 이미 계산된 맵을
조회만 하므로 **추가 계산 비용이 0이다.**

이건 실외 지도가 흉내낼 수 없는 차별점이다. 네이버가 직선거리로 근사하는 자리를 우리는
실제 보행 비용으로 채운다.

### 실패 조건 (먼저 정한 것)

- **출발 위치가 없을 때.** PDR 미시작·측위 실패면 `reachByNodeId`가 비어 있다.
  → 정렬을 적용하지 않고 **기존 순서를 그대로 둔다.** 절반만 정렬된 목록이 가장 나쁘다.
- **`nodeId == null`인 매장.** 거리를 못 구한다. → 정렬 대상에서 빼고 **목록 끝**에
  현재 상대 순서를 유지한 채 붙인다. A-2가 이미 이 경우 `경로 안내 불가`를 표시한다.
- **도달 불가 매장.** 그래프가 끊겨 `reachByNodeId`에 없는 경우도 위와 같이 처리한다.
- **의미 검색 결과의 순서를 뒤집는 문제.** `/query/ai`가 유사도순으로 준 결과를 거리로
  재정렬하면 "가장 의미가 맞는 매장"이 아래로 내려간다. → **경량 검색 결과에만
  적용하고, `_fromSemantic` 결과에는 적용하지 않는다.** 두 순서의 의미가 다르다.
- **정렬 안정성.** 거리가 같은 매장(같은 노드를 공유하는 인접 매장)이 매번 다른 순서로
  나오면 안 된다. 동점은 기존 순서를 유지하는 안정 정렬을 쓴다.

### 검증 기준

- [x] 출발 위치가 있을 때 결과가 거리 오름차순
- [x] 출발 위치가 없을 때 순서가 기존과 동일 (회귀 확인)
- [x] `nodeId == null` 매장이 목록 끝에 모임
- [x] 의미 검색 결과의 순서가 바뀌지 않음
- [x] 동점 거리에서 순서가 매 호출 동일 (결정적) — Dart `List.sort`는 32건을 넘으면
      불안정해진다. tie-breaker를 빼고 돌려 실제로 순서가 뒤바뀌는 것을 확인한 뒤
      테스트를 **동점 40건**으로 구성했다. 2~3건만 주면 삽입 정렬 경로라 우연히 통과한다.

### 배선하며 함께 고친 것 — 추천 이유가 옆 매장에 붙던 경로

`_discoveryMatches`를 `_results`와 **인덱스로** 짝지어 왔는데, 정렬이 들어오면 추천
이유가 다른 매장에 붙는다. 그리고 이 조합은 가정이 아니었다 — `_fromSemantic`은 결과
이름이 질의로 시작하면 `false`가 되는데(`search_panel.dart`) 그때도 `_discoveryMatches`는
차 있다. 즉 **정렬은 도는데 인덱스 짝짓기는 깨지는** 경로가 실제로 있었고, 타 층 매장을
정확한 이름으로 검색하면 그 경로를 탄다. `storeId` 기준으로 바꿨고, 인덱스 방식으로
되돌리면 그 테스트만 실패하는 것까지 확인했다.

## 실기기 검증 (2026-08-08, Galaxy S23 · SM-S918N)

USB로 붙여 `adb reverse tcp:8001`로 로컬 백엔드에 연결하고 확인했다. 새 엔드포인트가
Cloud Run에 아직 없어 배포 백엔드로는 자동완성이 뜨지 않는다.

**서버 실측이 문서 값과 일치했다.** `store-index` 341,135B / gzip 44,914B,
`/stores` 1,258,677B / gzip 254,748B. 순서 결정성·404도 확인했다.

화면으로 확인한 것 — `apc` 입력 시 `A.P.C. · 3F`·`A.P.C 골프 · 4F`가 즉시 뜨고,
서버 로그에 `/query/ai` 호출이 없다(2차 건너뛰기). 최근 검색어가 없는 첫 실행에서는
안내 문구가 그대로 남는다(J 검증 기준 1번).

### 실기기에서만 드러난 문제 셋

단위 테스트로는 잡히지 않았다. 셋 다 "화면은 멀쩡한데 사용자가 원하는 곳에 못 가는"
종류다.

**1. 야외에서 실내 인덱스를 쓰고 있었다.** 시청 앞 야외 지도에서 `apc`를 쳤더니
더현대서울 3층 매장이 후보로 떴다. 후보 원본이 건물 하나의 매장 목록이라 야외에서는
의미가 없다. 이제 `_indoorContextActive`가 참일 때만 후보를 만들고 **목록도 받지
않는다** — 야외에서 쓰지도 않을 341KB를 내려받을 이유가 없다.

> 야외 장소 검색은 외부 검색 API(Tmap 등)로 따로 채울 예정이며, 그 설계는 아직
> 정해지지 않았다. **이 문서의 K~N은 실내 한정이다.**

**2. 맞는 답을 의미 검색이 틀린 답으로 갈아치웠다.** 흐름이 이랬다.

1. 자동완성이 `A.P.C. · 3F`를 즉시 표시
2. 스피너가 그걸 덮음(`취향에 맞는 매장을 찾는 중...`)
3. 의미 검색이 **`6A`(주차·B5)·`6E`(주차·B4)** 를 "뜻이 비슷한 매장"이라며 확정

서버 경량 매칭은 `name LIKE %apc%`라 구두점이 든 `A.P.C.`를 못 잡고 `no_match`를 준다.
그러면 2차로 넘어가고, 임계값을 겨우 넘긴 결과가 자신 있게 오답을 낸다
([FAISS.md 11-1](https://github.com/Routex-labs/fastapi/blob/main/docs/native/FAISS.md)의 "자신 있게 틀리는" 사례와 같은 종류다).

**온디바이스 이름 후보는 임베딩 결과에 덮이지 않는다.** FAISS.md 11절의 역할 분리
("정확한 이름은 1차가 확정하고 임베딩은 말로 푸는 질의만 담당")를 그대로 따르는
것이고, 달라진 건 그 1차가 서버뿐 아니라 온디바이스 인덱스이기도 하다는 점이다.
교정 후보만 있을 때는 추측이라 2차에 기회를 준다.

> **2026-08-09 정정 — 차단 지점을 호출 전에서 응답 후로 옮겼다.** 처음 구현은 이름
> 후보가 있으면 `/query/ai` **호출 자체**를 막았는데, 그건 필요보다 넓은 차단이었다.
> 막아야 했던 것은 임베딩 추측이지 그 엔드포인트가 아니다 — `/query/ai`의 1차는
> 임베딩이 아니라 서버 어휘(동의어·intent·카테고리)이고, 이름 매칭과 같은 등급의
> 결정적 매칭이다. 자세한 근거와 실측은 아래 **V절**에 있다.

**3. 후보를 탭해도 매장에 못 갔다 — 2번을 고치다 넣은 회귀.** 1F에서 3F의 `A.P.C.`
후보를 탭하면 그 이름으로 다시 검색하는데, **층 스코프** 때문에 1차가 또 빈손이 되어
후보 화면으로 되돌아온다. 몇 번을 눌러도 매장에 닿지 못한다. 원래는 2차가 층을 무시하고
건물 전체를 봐서 복구했는데(search-qa-fix-wave Wave 1), 2번 수정이 그 복구 경로까지
막았다.

**목록에서 고른 검색은 층으로 좁히지 않는다.** 층 스코프는 사용자가 직접 친 `화장실`
같은 시설 질의를 지금 보는 층으로 확정하려는 것이지, 목록에서 특정 대상을 콕 집은
행동에 적용할 이유가 없다. 최근 검색어 탭도 같은 성격이라 함께 적용했다.

> 좌표를 `store-index`에 되돌려 넣고 탭 즉시 이동시키는 안(+194KB)도 있었으나,
> 층 스코프만 빼면 서버가 `ok · 3F`를 그대로 주므로 **페이로드도 추가 요청도 없이**
> 해결된다.

## V. 이름 후보가 카테고리 검색을 가리던 문제

> 항목 번호는 [검색 결과 목록 UX](search-result-list-ux.md)의 U 다음을 이어받는다.

### 문제 — 실기기에서 확인 (2026-08-09, SM-S918N)

`커피`를 치면 상호에 "커피"가 든 **4곳(전부 B1)** 만 뜨고 끝났다. 서버는 같은 질의에
카페 **53곳**을 `results`로 돌려줄 수 있었는데 클라이언트가 묻지를 않았다. 검색어 6개를
치는 동안 `/query/destination`은 6번, `/query/ai`는 2번만 호출됐다.

원인은 K절 실기기 검증 2번의 규칙이었다. "이름 후보가 있으면 2차로 넘기지 않는다"가
`/query/ai` **호출 자체**를 막았는데, 막아야 했던 것은 임베딩 추측이지 그 엔드포인트가
아니었다. `/query/ai`의 1차는 임베딩이 아니라 서버 어휘(동의어·intent·카테고리)이고,
이름 매칭과 같은 등급의 결정적 매칭이다.

가로채는 경로가 둘이었고, 둘째는 결과 자체가 틀렸다.

| 질의 | 화면 | 서버가 줄 수 있던 것 |
|---|---|---|
| `커피` | 더커피·도조 커피·카멜커피·해례커피 | 카페 53곳 |
| `카페` | 카페 H·카페 레이어드 | 카페 53곳 |
| `옷` | **오설록·바오 서울** (자모 매칭, 업종 무관) | 스타일 되묻기(컨템포러리 61·캐주얼 50·명품 42…) |
| `밥` | **바버(컨템포러리)·바바라(이너웨어)** | — (어휘 밖이라 임베딩) |
| `골프` | 5곳(상호에 "골프"가 든 것만) | 골프 12곳 되묻기 |
| `안경` | 2곳 | 아이웨어 10곳 |

### 규칙 — 한 줄

> **온디바이스 이름 후보는 임베딩(`semantic`)에는 이기고, 서버 어휘(`light`)에는 진다.**

A.P.C. 불변("임베딩은 이름 후보를 덮지 못한다")은 글자 그대로 유지되고, 차단 위치만
호출 전 → 응답 후로 옮겼다.

### 배제한 대안 — 둘 다 실측으로 떨어졌다

- **`/query/destination`의 `status`를 신호로 쓰기.** 이 값은 층 스코프가 걸린 뒤라
  1F에서 `커피`가 `no_match`로 나온다(카페가 1F에 없어서). 사용자가 선 층에 따라 검색
  구조가 달라지는 설계는 쓸 수 없다.
- **클라이언트 단독 휴리스틱**(후보 수와 카테고리 규모 비교 등). `커피`→카페는 서버만
  가진 동의어·intent 어휘다. 클라가 흉내 내면 사전이 두 벌이 되어 반드시 한쪽이 썩는다.

그래서 **서버가 자기가 어느 경로로 답했는지 알려주는** 쪽으로 갔다 —
`DiscoveryResponse.source`(`light` | `semantic`). additive 필드라 구버전 클라이언트는
무시하고, 필드가 없는 구버전 서버에 붙으면 `unknown`으로 떨어져 오늘 동작이 유지된다.

### 실패 조건 (먼저 정한 것)

- **버전 어긋남.** 구서버+신클라 → `source` 없음 → semantic 취급 → 이름 후보가 이긴다
  (오늘 동작). 신서버+구클라 → 필드 무시 → 오늘 동작. **어느 조합도 회귀가 없다.**
  폴백이 `light`로 기울면 그 순간 A.P.C. 회귀가 되살아나므로 방향을 명시해 둔다.
- **후보가 스피너에 덮이는 것.** A.P.C. 사고의 절반은 "맞는 답을 보여주다가 «찾는 중»
  으로 덮은 것"이었다. 이름 후보가 떠 있으면 2차 대기 중에도 스피너를 띄우지 않는다.
- **어휘인데 빈 결과.** 지금 서버 구현에서는 `light` + 빈 `matches`가 나올 수 없지만,
  그 전제가 깨지면 화면의 맞는 후보가 "결과 없음"으로 지워진다. 빈 결과도 버린다.
- **2차 실패.** 후보가 떠 있는 동안의 네트워크 오류는 후보 화면을 덮지 않는다.
- **배너 문구.** 어휘로 찾은 결과에 "뜻이 비슷한 매장"을 붙이면 정확히 찾아 준 것을
  추측이라고 말하는 셈이다. `source`가 `semantic`일 때만 붙인다.

### 검증 기준

- [x] `커피`가 카페 53곳을 보여준다 — 실기기 확인. 화면 머리말이 `검색 결과 53 · 5개 층`
- [x] `옷`이 스타일 되묻기로 간다(오설록·바오 서울이 아니라) — 실기기 확인
- [x] `apc`가 `A.P.C. · 3F`·`A.P.C 골프 · 4F`를 그대로 유지한다 — 실기기 확인.
      서버는 이 질의에 `source: semantic`으로 주차구역 2건을 줬고, 클라이언트가 버렸다
- [x] `밥`은 이름 후보를 유지한다(서버가 임베딩으로 답하므로) — 실기기 확인
- [x] 어휘 결과에 "뜻이 비슷한" 배너가 붙지 않는다 — 위젯 테스트 + 실기기
- [x] `source`가 없는 응답은 이름 후보를 대체하지 않는다 — 위젯 테스트
- [x] 상단 검색 패널과 길찾기 시트가 같은 규칙을 쓴다 — 양쪽 위젯 테스트

### 이 변경이 고치지 않는 것

- **`밥`** — 서버 어휘에 없어 임베딩(대도 깍밥·요즘김밥, 사람 눈에는 정답)이 오는데,
  규칙상 이름 후보(바버·바바라…)가 이긴다. A.P.C. 원칙의 대가다. 후속 선택지는 후보
  아래에 "뜻이 비슷한 매장"을 **교체가 아니라 덧붙이는** 것.
- **`안경`·`와인`·`케이크`** — 서버가 `direct` 1건으로 확정한다(금강 안경·와인웍스·
  블랑 케이크). 아이웨어 10곳 풀이 아니다. 이건 클라이언트 게이트가 아니라 서버
  `discover`의 확정 판정 문제라 별도 항목으로 남긴다 — 근본 해법은 `안경`→`아이웨어`
  같은 동의어 보강 쪽으로 보인다.

## W. 트리거는 엔터가 아니라 「타이핑이 멎었다」 <sub>완료</sub>

`SearchPanel`이 언제 무엇을 부르고 화면 단계를 어떻게 정하는지의 단일 출처다.
코드는 [`search_panel.dart`](../../client/lib/screens/map_shell/widgets/search/search_panel.dart).

### 문제

의미 검색을 엔터에만 붙였더니 둘이 깨졌다
([conversational-discovery.md](https://github.com/Routex-labs/fastapi/blob/main/docs/native/conversational-discovery.md) 1-2).

- 한글 IME에서 첫 엔터가 조합 확정에 쓰이면 `onSubmitted`가 오지 않아 `submitTick`이
  오르지 않는다. 의미 검색이 시작조차 안 한다.
- 그동안 화면에는 경량이 빈손이라는 이유만으로 "찾지 못했어요"가 최종 결론처럼 떠 있다.
  `신발`·`밥집`은 타이핑만으로는 **항상** 그 화면이었다.

### 규칙 — 디바운스 두 단

| 단계 | 대기 | 호출 |
|---|---|---|
| 1차 경량 | 타이핑이 멎고 300ms | `/query/destination` |
| 2차 의미 | 1차가 빈손이면 **400ms 더** | `/query/ai` |
| 엔터(`submitTick`) | 두 대기를 건너뛴다 | 같은 경로 |

**경량까지 700ms로 늦추지 않는 이유**는 이름을 정확히 아는 흔한 검색이 같이 느려지기
때문이다. 의미 검색은 경량과 비용이 자릿수로 달라, "타이핑이 잠깐 멈췄다"가 아니라
"손을 뗐다"에 가까운 신호에서만 태운다. 반대로 2차 대기를 0으로 두면 `밥`·`밥 먹`·
`밥 먹을`이 전부 모델을 태운다.

두 요청 모두 `current_floor_id`를 함께 보낸다 — "화장실"처럼 층 시설을 가리키는 질의를
지금 보는 층으로 확정하기 위해서다. 매장 이름이 다른 층에 있어 1차가 빈손이 되더라도,
2차는 층을 무시하고 건물 전체를 보므로 그대로 찾아낸다.

### 상태는 두 값으로만 받는다

패널은 `query`·`submitTick`만 받고 명령형 호출은 두지 않는다. **순서 문제** 때문이다 —
패널은 검색이 활성화될 때 비로소 트리에 들어오므로, 상위가 GlobalKey로 메서드를 부르면
첫 글자가 패널이 생기기 전에 도착해 조용히 사라진다.

단계도 불리언 두 개(`_searching`·`_searchingSemantic`)가 아니라 enum 하나다. "경량은
끝났지만 의미는 아직"이라는 단계가 생기면서 조합만으로는 화면을 정할 수 없게 됐고,
특히 `noMatch`는 **2차까지 끝났을 때만** 들어갈 수 있어야 하는데 불리언으로는
"검색 안 하는 중 + 결과 없음"과 구분되지 않는다.

### 화면을 고르는 두 규칙

- **후보를 띄울지는 단계가 아니라 「이번 글자의 답이 있는가」로 정한다.** `_phase`로
  판단하면 안 된다 — 디바운스 300ms 동안에는 요청이 시작조차 안 해 단계가 그대로 남아
  있다(첫 글자엔 `idle`, 두 번째 검색부터는 **직전 질의의 `results`**). 단계만 보면
  사용자가 이미 다른 말을 치는데 화면은 이전 결과를 계속 보여준다. 그래서 지금 화면에
  그려진 결과가 어느 질의의 것인지(`_submittedQuery`)를 검색창 글자와 비교한다.
  온디바이스 후보는 0ms에 나오니 그 사이를 후보로 채운다.
- **건물 밖 결과가 하나라도 있으면 어떤 단계에서도 목록을 보여준다.** 실내가 아직 돌고
  있거나(스피너)·빈손이거나·실패했더라도, 찾던 곳이 바깥에 이미 잡혀 있는데 그 화면들을
  띄우면 답을 손에 쥐고도 못 보여 주는 셈이다. 실내가 도는 중이라는 사실은 목록 안의
  진행 줄이 대신 알린다. 바깥 검색은 실내와 독립이라 실패해도 단계를 건드리지 않는다.

## N. 매장 소개 텍스트 보강 <sub>장기 — 이번 범위 밖</sub>

### 문제

FAISS 재현율이 안 오르는 근본 원인이다. ATM(0.464)·타임파리(0.453)가 임계값을 못 넘는
이유가 [FAISS.md 11-1](https://github.com/Routex-labs/fastapi/blob/main/docs/native/FAISS.md)에 그대로 적혀 있다 — **facet도 설명도
없는 매장**이라 인덱스 문서가 상호 하나뿐이다.

`store_details` 스키마에는 이미 `summary`(60자 소개)·`tags` 필드가 있는데,
**채워진 매장이 1건**(스타벅스)이다.

### 방향

`summary`를 채워 인덱스 문서에 넣으면 그게 우리 버전의 "리뷰 텍스트"다. 다만 1640건
수작업이고, 이미 밀려 있는 facet 검수 트랙(W8, 262건 미착수)과 같은 병목이다.

**이번 작업에 넣지 않는다.** K·L이 들어가면 애매한 질의 자체가 줄어들어 N의 시급성이
어떻게 변하는지 먼저 보고 판단한다.

## 해결됨 — `client/test/`가 CI에서 돌지 않던 문제

`.github/workflows/ci.yml`이 `flutter test test/`만 실행해서, 표준 Flutter
디렉터리인 `client/test/` 아래 테스트가 **작성돼 있으면서도 회귀를 막지 못하는** 상태였다.
`flutter test test/`를 CI에 추가했다(로컬 전량 통과 확인 후). 이 문서의 K·L·M 테스트도
그 디렉터리에 있으므로 이제 CI가 지켜 준다.

테스트 디렉터리가 `tests/`와 `test/` 둘로 갈린 것 자체는 그대로 남아 있다. 합치는 것은
이 문서 범위가 아니다.

| 순위 | 항목 | 상태 |
|---|---|---|

| 1 | **M** 거리순 정렬 | ✅ 완료 — 로직·배선·테스트 |
| 2 | **K** 자동완성 | ✅ 완료 — 실데이터 1640건 후보 순위 20/20 |
| 3 | **L** 오타 교정 | ✅ 완료 — 하한 3글자 유지(위 확정 절) |
| 4 | **J** 최근 검색어 | ✅ 완료 — 저장소·idle 화면 |
| 5 | **V** 이름 후보가 카테고리 검색을 가리던 문제 | ✅ 완료 — `source` 계약·양쪽 화면·실기기 |
| — | **N** 텍스트 보강 | 미착수 — K·L 효과를 보고 판단 |

자동 검증 기준은 전부 충족했고, 실기기 확인도 마쳤다(위 「실기기 검증」). 남은 것은
**한글 입력이 필요한 두 케이스**다 — 초성 `ㄴㅇㅋ`와 오타 교정 `샤낼 뷰티`. `adb`로는
한글을 보낼 수 없어 자동화하지 못했고, 로직 자체는 실제 매장명 fixture로 덮여 있다.

**야외 검색은 이 문서 범위 밖이다.** K~N은 실내 한정이며, 야외는 외부 검색 API로
따로 채운다(설계 미정).
